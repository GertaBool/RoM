# Headless harness: run the real DLL without the game

The harness loads a real `CvGameCoreDLL.dll` built from Rise of Mankind source in
`harness.exe`, a small Windows console program run under Wine. It loads the mod's
XML, sets up a scripted map and lets the AI play for some turns. The DLL's own
code makes every decision: unit AI, missions, movement, cargo, founding, the
economy and turn processing. The harness stands in for the game executable and
supplies only what the executable would.

It was written to find out why settlers stayed aboard ship off the coast
([research/landing-engine](../../research/landing-engine/README.md)). The unit
tests had passed because their stand-ins for engine functions behaved differently
from the real ones. In this harness those engine functions are the real DLL code.

## What is real and what is substituted

| Part | In the harness |
|---|---|
| Game rules, AI, units, cities, turns (`CvGameCoreDLL.dll`) | Real, built from the mod source with MSVC 2003 |
| Path finding (`FAStar`) | A* that calls the DLL's own cost, validity and heuristic callbacks, as the engine does |
| XML loading (`FXml`) | Small DOM parser behind the engine's XML interface; the mod's XML and schemas load through the DLL's own loader |
| Base-game XML that the mod does not ship | Generated by `gen_bts_xml.py`: enum-bound files from the DLL's `CvEnums.h`; gameplay tables (goodies, hurries, sea levels, vote sources, landscapes) copied from AdvCiv, which carries them unchanged from BTS; one placeholder entry for interface, camera and art lists |
| Python | Inert. Python reports itself uninitialized, so the DLL skips Python events. Callbacks whose result the DLL reads anyway get the defaults of BTS `CvGameUtils.py` / RoM `RoMGameUtils.py` (`engine.cpp`, `pythonDefault`); the RoM rules that change the game are mirrored in C++ (see Limits) |
| Graphics, sound, network, interface | Neutral return values (`engine_stubs.h`, generated from the SDK interface headers) |
| Map and starting units | Placed through `HarnessHooks.cpp`, extra DLL exports compiled only into harness builds; they call the DLL's normal setup functions |

Limits: Python game logic does not run. The parts of RoM's Python that change
the game are computed in C++ the way the Python does:

- `calculateScore`, `doCityCaptureGold`, `doPillageGold` (`HarnessScenario.cpp`).
- `cannotConstruct`, `getBuildingCostMod`, `getUnitCostMod` and the
  building-built and begin-player-turn events of `RoMEventManager.py`
  (`HarnessRoM.cpp`): the building upgrade lines (a library replaces the
  school of scribes, a fair the market, and so on: the replaced building is
  removed and cannot be built again), the observatory, Copernicus and Djenne
  terrain conditions, zCivics building prerequisites, the civic and Djenne cost
  discounts, and the Djenne, World Bank and Crusade effects. `build_dll.sh`
  generates the upgrade-line and prerequisite tables from the mod's Python
  (`gen_rom_tables.py`) and adds the two event calls to its copy of
  `CvEventReporter.cpp`.

Without the upgrade lines a city keeps every tier of a line, and late-game
harness cities grew and earned far more than in the game. Not mirrored:
`getUpgradePriceOverride` (Personal Replicators), the Nanite Defuser and Eden
effects, and Enhanced Tech Conquest's research points for a conquered city.
In the scripted islands mode only one player is on the map and barbarians, huts
and events are off. Results show what the DLL's code does; they do not prove
that the game client behaves the same everywhere.

The stand-in Python objects allocate nothing per call. Earlier versions
allocated a few hundred bytes for every callback the DLL prepared, hundreds of
thousands per late-game turn. On a Mediterranean Marathon game the process grew
to 4 GB and crashed at turn 491; the same game with the fix (identical
telemetry up to that turn) used under 100 MB and ran to its end.

## Inputs

- The toolchain from [toolchain/README.md](../README.md), with `VCTOOLKIT_DIR`,
  `PSDK_DIR`, `BTS_SDK_DIR` and `WINEPREFIX` set.
- A Rise of Mankind checkout (its `Assets/` is loaded as the mod).
- `Assets/XML` of an [AdvCiv](https://github.com/f1rpo/AdvCiv) checkout, for the
  base-game tables listed above.
- Host tools: `python3`, `objdump`, `llvm-undname`, `lld-link`.

## Use

```sh
cd toolchain/harness
# once: engine stubs, base-game XML, inert python24/boost_python DLLs
./setup.sh <rom>/Assets/CvGameCoreDLL <advciv>/Assets/XML ../../builds/0011/CvGameCoreDLL.dll
# a harness DLL per source tree to compare ("log" turns on BBAI logging)
./build_dll.sh <rom-before>/Assets/CvGameCoreDLL work/b-before log   # or "profile"
./build_dll.sh <rom-after>/Assets/CvGameCoreDLL work/b-after log
./build_harness.sh work/b-after
./compare.sh 30 <rom-after> before=work/b-before after=work/b-after
MODE=plain ./compare.sh 30 <rom-after> before=work/b-before after=work/b-after
```

`setup.sh` takes the list of Boost.Python imports from any built DLL; those
imports have not changed between patches. Each build gets a game folder
`work/root-<name>` with `run-<scenario>.log` (turn snapshots of every unit, city
and the economy) and `bbai-<scenario>.log` (the DLL's BBAI log). A harness DLL
build takes about two minutes. A 30-turn scenario runs in a few seconds.

## Scenarios

The player has a capital on the east shore of a 3x3 island, with no room for a
second city. It starts with a settler (`UNITAI_SETTLE`), two warriors
(`UNITAI_CITY_DEFENSE`) and a galley (`UNITAI_SETTLER_SEA`). An empty, revealed
island lies to the east:

| Scenario | East island starts at x = | Best site distance |
|---|---|---|
| `islands` | 17 | 6 tiles, one sailing turn |
| `mid` | 21 | 10 tiles, two sailing turns |
| `far` | 27 | beyond the AI's settlement candidate range; no voyage is expected |

By default the start has Settler difficulty, 1000 gold and a size-3 capital, so
unit upkeep cannot disband the ship or escort mid-test. `MODE=plain` uses Noble
difficulty without either. Both modes gave the same landing results.

## Real saves

A `.CivBeyondSwordSave` from the game (save format 302) loads into the DLL's own
`read()` functions, in the order the executable uses: `CvInitCore`, game, map,
teams, players.

```sh
python3 sav2dat.py "My Game.CivBeyondSwordSave" work/mygame   # -> mygame.init, mygame.game
cp work/mygame.init work/mygame.game work/root-after/
cd work/root-after
wine harness.exe save mygame.init mygame.game 10 run.jsonl 5 20000
```

Arguments: turns to play, telemetry file, a detailed telemetry line every N
turns, and the number of `CvGame::update` calls after which a turn counts as
stuck. Human seats are handed to the AI (autorun). For every turn the log prints
`turn T (ms, updates)`; a turn that does not end prints `STUCK` reports naming
the groups that keep it open, and stops after four times the limit. The run
writes `run.jsonl.state0.json` and `.state1.json`: every player's economy,
techs, civics, cities (buildings, current order) and settlers.

`HARNESS_RESEED=n` restarts the game's synchronized random sequence from `n`
after loading, so one save gives several independent continuations (for
comparing builds by more than one trajectory).

The game reads `res/Fonts/GameFont_GlobalDefines.xml` differently from the
harness; saves record 16 religions and 27 corporations, so the harness skips that
file unless `HARNESS_GAMEFONT=1`.

Diagnostics in the state files, off by default because they run extra searches:

| Variable | Adds |
|---|---|
| `HARNESS_SETTLER_DIAG=1` | per settler: escort, horizon, and for the eight best settlement candidates every filter `AI_found` applies (can found, enemy units, other parties, path with and without `MOVE_SAFE_TERRITORY`, delivery region) and the transport of a settler at sea |
| `HARNESS_VALUE_DIAG=1` | per AI city: the twelve buildings with the highest `AI_buildingValue`, with cost and turns |
| `HARNESS_HISTORY_DIAG=1` | what the save remembers: each player's per-turn score, economy, industry, agriculture, power and culture history from turn 0, research progress and queue, cost terms, every unit (type, role, experience, position), the AI's value of every civic it may adopt; for the game, the replay messages (city foundings, civic adoptions, wars, first techs) and the number of units of each type created |

## WorldBuilder scenarios

`wbs2scn.py` converts a `.CivBeyondSwordWBSave` (version 11) into a flat file
that `HH_loadScenario` applies in the order `CvWBDesc.py` does: plots, teams,
players, units, cities. All players are AI.

```sh
python3 wbs2scn.py Mediterranean.CivBeyondSwordWBSave work/med.scn
wine harness.exe scenario med.scn GAMESPEED_EPIC HANDICAP_NOBLE 1 200 med.jsonl 10
```

Arguments: speed (`-` keeps the file's), difficulty, map random seed, turns,
telemetry file, detailed line every N turns.

Each turn line holds every player's economy (`bld` is the number of buildings
in its cities), attitude toward each met player and,
on detailed lines, the attitude components and memories; the team matrix (met,
war, open borders, defensive pact, vassal, war plan, war success); and the turn's
events: standing deals opened and ended, cities founded, captured or razed,
eliminations, and every trade as it is agreed (`{"trade":[a,b],"ai":[...],"bi":[...]}`,
items as `[TradeableItems, data]`). One-time trades (techs, gold, maps, cities)
never stand as deals, so `build_dll.sh` adds a call to `HH_noteTrade` at the top
of its copy of `CvDeal::addTrades`; the source tree is not changed.

The telemetry does not change the game. Many AI getters fill a per-turn cache
on first use (attitudes, strategy and victory hashes, upgrade costs, city
closeness and yield ranks), and `AI_getStrategyRand` may draw a synchronized
random number. Called at the turn boundary they would compute those values
earlier than the game does: with the earlier telemetry the same seed gave a
different game from turn 38 on. `HarnessPeek.h` saves those caches and the
random seeds before the telemetry, the stuck report and the state dump, and
restores them afterwards (`build_dll.sh` declares it a friend of `CvPlayerAI`,
`CvCityAI` and `CvCity` in its copy). Check: `HARNESS_TELEMETRY_MINIMAL=1`
leaves out attitudes, components and memories; a 200-turn Epic game is the
same with and without it.

## Snapshots, random log and reload checks

| Variable | Effect |
|---|---|
| `HARNESS_SNAPSHOT=t1,t2,...` | At the start of each listed game turn (scenario or save mode) write `<telemetry>.t<turn>.init` and `.game`, which `harness.exe save` loads like a converted save; `.game.idx` lists where the game, map, each team and each player end in the stream |
| `HARNESS_SNAPSHOT_OBJECTS=1` | With a snapshot, also write every plot group, city, unit and selection group on its own (`.game.obj`, index `.game.objidx`) to locate a difference between two snapshots |
| `HARNESS_RAND_LOG=t` | From game turn `t` on, log every random number the DLL draws, with its purpose, to `logs\rand.log`: two runs can be compared draw by draw |

A snapshot taken late in a game can be continued many times (with
`HARNESS_RESEED`) and with different builds, without replaying the turns before
it. Loading a snapshot and writing it again at once gives the same bytes, apart
from one replay message the load adds and the slot claims `CvInitCore::read`
converts. A game continued from a snapshot should play exactly like the game
that wrote it; where it does not, the DLL keeps state between turns that a save
does not carry, and in multiplayer a rejoining player would go out of sync.
Found this way, with the random-number log locating the first differing draw:
the team counters (turns at war, at peace, shared war) advanced a turn before the
attitudes that use them were refreshed (fixed in patch 0014), and the AI's
border-danger flags were set where nothing was known and never cleared (fixed in
patch 0015). With both fixes a continuation from a turn-start snapshot is identical
to the running game (`research/diplomacy/tools/roundtrip.sh`).

## Profiling

`./build_dll.sh <src> <out> profile` builds with `FP_PROFILE_ENABLE`: every
`PROFILE` scope reports to the harness, and a save run ends with a table of self
and inclusive time and call counts (`HARNESS_PROFILE_SORT=incl` sorts by
inclusive time). Profiled builds are several times slower; use them for shares,
plain builds for timings.
