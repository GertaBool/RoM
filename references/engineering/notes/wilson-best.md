## What it says
- p. 1 (Introduction, opening summary): "most scientists are never taught how to do this efficiently." -- so many are unaware of tools and practices for more reliable and maintainable code with less effort.
- p. 1 (Introduction): "scientists typically spend 30% or more of their time developing software" -- yet "90% or more of them are primarily self-taught", lacking practices such as version control, code reviews, unit testing and task automation.
- p. 1 (Introduction): "We believe that software is just another kind of experimental apparatus" -- to be built, checked and used as carefully as physical apparatus, though most scientists "do not know how reliable their software is".
- p. 1 (Introduction): "This can lead to serious errors impacting the central conclusions of published research" -- evidence: retractions, technical comments and corrections in Science, PNAS, J Mol Biol, Ecology Letters, J Mammalogy, JACC, Hypertension and The American Economic Review.
- p. 1 (Introduction): "computing errors can have disproportionate impacts on the scientific process." -- because software is reused; an error in another group's code caused several retractions and was not found until after publication.
- p. 1 (Introduction): "not everything must be done to the most exacting standards" -- but scientists need to know best practices to improve their work and review others'.
- p. 1 (Introduction): "None of these practices will guarantee efficient, error-free software development, but used in concert they will reduce the number of errors in scientific software" -- based on decades of experience, reports from other groups, guidelines and empirical studies.
- p. 1 (Introduction): "we do not discuss the equally important (but independent) issues of reproducible research, publication and citation of code and data, and open science." -- stated limit of scope.
- p. 2 (Write Programs for People, Not Computers): "If software cannot be easily read and understood, it is much more difficult to" know that it does what is intended; human working memory is limited, pattern matching finely tuned, attention span short.
- p. 2 (1a): "a program should not require its readers to hold more than a handful of facts in memory at once" -- achieved by breaking programs into functions that each conduct a single, easily understood task.
- p. 2 (1b): "scientists should make names consistent, distinctive, and meaningful" -- names like a, foo, results and results2 cause confusion.
- p. 2 (1c): "scientists should make code style and formatting consistent" -- mixed indentation or naming makes code take longer to read and readers make more mistakes.
- p. 2 (Let the Computer Do the Work): "sooner or later even the most careful researcher will lose focus while doing this and make mistakes." -- hence make the computer repeat tasks (2a) and save recent commands in a file for re-use (2b).
- p. 2 (2c): "use a build tool to automate workflows" -- specify how intermediate files and results depend on each other and on the programs that create them, "so that a single command will regenerate anything that needs to be regenerated."
- p. 3 (provenance): "everything needed to recreate the output should be recorded automatically in a format that other programs can read." -- called the provenance of data.
- p. 3 (provenance): what can be recorded without additional tools: "unique identifiers and version numbers for raw data records" and for programs and libraries; "the values of parameters used to generate any given output" and the names and version numbers of programs used.
- p. 3 (Make Incremental Changes): "scientists often can’t know what their programs should do next until the current version has produced some results." -- requirements are rarely frozen, which challenges design by up-front specification.
- p. 3 (3a): "Programmers are most productive when they work in small steps with frequent feedback and course correction" -- typically steps of about an hour grouped in iterations of about a week, producing working (if incomplete) code after each.
- p. 3 (3b): "Two of the biggest challenges scientists and other programmers face when working with code and data are keeping track of changes" -- and collaborating; emailing or shared folders "can lead to confusion and lost work".
- p. 3 (3b): "The standard solution in both industry and open source is to use a version control system" -- it stores snapshots, highlights conflicts and stores the entire history with metadata on what was changed and by whom.
- p. 3 (3b): "the best one to use is almost always whatever your colleagues are already using" -- of Git, Subversion, Mercurial and hosting services.
- p. 3 (3c): "Reproducibility is maximized when scientists put everything that has been created manually in version control" -- including programs, original observations and paper sources; "Automated output and intermediate files can be regenerated as needed."
- p. 3 (3c): for binary files "it is often more sensible to use an archiving system for them, and store the metadata describing their contents in version control instead"
- p. 3 (Don't Repeat Yourself): "Anything that is repeated in two or more places is more difficult to maintain." -- each change must be made in several places, increasing errors and inconsistencies.
- p. 3 (4a): "every piece of data must have a single authoritative representation in the system" -- constants defined once, raw data files with a single canonical version, locations given IDs.
- p. 3 (4b): "Avoiding ‘‘code clones’’ has been shown to reduce error rates" -- so modularize code rather than copy and paste; a fix then takes effect everywhere and the mental model stays accurate.
- p. 3 (4c): "it is vital that scientific programmers re-use code instead of rewriting it" -- better to find an established library for well established problems.
- p. 3 (Plan for Mistakes): "While no single practice has been shown to catch or prevent all mistakes, several are very effective when used in combination"
- p. 3 (5a): "Experienced programmers add assertions to programs to check their operation" -- "because experience has taught them that everyone (including their future self) makes mistakes."
- p. 4 (5a): "Assertions can make up a sizeable fraction of the code in wellwritten applications" -- they halt the program immediately when something goes wrong, and "assertions are executable documentation" that the reader can be sure are accurate and up to date.
- p. 4 (5b): automated tests check units, combinations (integration) and that "the behavior of a program doesn’t change when the details are modified (regression tests)." -- use an off-the-shelf unit testing library.
- p. 4 (5b): "Tests check to see whether the code matches the researcher’s expectations of its behavior, which depends on the researcher’s understanding of the problem at hand" -- often by comparing to simplified cases, experimental data or trusted earlier programs.
- p. 4 (5c): "turn bugs into test cases" -- write a test that triggers a found bug, which "(once fixed) will prevent the bug from reappearing unnoticed."
- p. 4 (5d): "reasonably complex code will always initially contain bugs." -- a symbolic debugger lets users see exactly how code executes, more productive than print statements or scrolling through log output.
- p. 4 (6a): "even experts find it hard to predict which parts of any particular program will be performance bottlenecks" -- make it work correctly, decide whether speeding up is worth it, then use a profiler.
- p. 4 (6b): "most programmers write roughly the same number of lines of code per unit time regardless of the language they use" -- so write in the highest-level language possible and move to C or Fortran only when sure.
- p. 4 (6b): "Programmers can also use a high-level prototype as a test oracle for a high-performance low-level reimplementation" -- comparing the optimized program's output with its simpler predecessor.
- p. 4 (7a): "inline documentation that recapitulates code is not useful." -- document interfaces and reasons, not implementations, e.g. a description of what a function does and its inputs and outputs.
- p. 5 (7b): "it is better to refactor code in preference to explaining how it works" -- the onus is on the author to convince peers that code is intrinsically difficult.
- p. 5 (7c): "embed the documentation for a piece of software in that software" -- which "increases the probability that when programmers change the code, they will update the documentation at the same time."
- p. 5 (Collaborate): "A large body of research has shown that code reviews are the most cost-effective way of finding bugs in code" -- they also spread knowledge and keep it when people leave.
- p. 5 (8a): "Experience shows that if reviews don’t have to be done in order to get code ... into the repository, they will soon not be done at all" -- so use pre-merge code reviews.
- p. 5 (8b): "Several studies have found that pair programming improves productivity" -- but many find it intrusive, so use it when bringing someone new up to speed and for tricky problems.
- p. 5 (8c): "use an issue tracking tool (8c) to maintain a list of tasks to be performed and bugs to be fixed"
- p. 5 (Conclusion): "if software is not version controlled, readable, and tested, the chances of its authors (much less anyone else) being able to recreate results are remote."
- p. 5 (Conclusion): "Our 24 recommendations are a beginning, not an end."
- p. 5 (Conclusion): "the time cost of implementing these kinds of tools and approaches in scientific computing is almost immediately offset by the gains in productivity" -- and the practices reinforce one another.
- p. 5 (Conclusion): "we do not recommend that research groups attempt to implement all of these recommendations at once" -- they should be introduced incrementally.
- p. 1 (Competing Interests): "The lead author (GVW) is involved in a pilot study of code review in scientific computing with PLOS Computational Biology." -- declared interest.

## Readings for our work
- Make each analysis document regenerable by one command that follows declared dependencies (save and logs to DuckDB tables to registry to rendered document), and never edit generated files by hand; a check can compare a fresh render with the committed file. Rests on: 2c build tool (p. 2), 3c manual content in version control and generated output regenerated (p. 3). Would not apply if: a document has no machine-generated part.
- Record provenance automatically with every figure and experiment result: save or log identifier, DLL build hash, XML version, harness parameters and seeds, and tool versions. Rests on: provenance list (p. 3). Would not apply if: the registry already stores these fields, in which case check that it does.
- Keep one authoritative copy of each fact: XML effects are read from the XML, not restated in notes; constants such as run counts live in one place. Rests on: 4a single authoritative representation (p. 3), DRY (p. 3). Would not apply if: a copy is generated from the source and checked against it.
- Make commits small and single-purpose (one concern per commit, with the line-ending normalisation separate from content changes), which keeps review and revert possible. Rests on: 3a small steps (p. 3), 3b version control for tracking and reverting (p. 3). Would not apply if: the changes cannot be separated without breaking the build.
- When a bug is found in a tool or in the DLL patch, add a regression test that triggers it before fixing; this ties checks to observed failures rather than adding checks speculatively. Rests on: 5c bugs into test cases (p. 4). Would not apply if: the failure cannot be reproduced deterministically.
- Pre-merge review by someone other than the author is the defence the authors rate most cost-effective; for our checks written by the same hand they check, at least require a separate review pass (another session or person) before a check is trusted. Rests on: code reviews most cost-effective (p. 5), reviews not required are soon not done (p. 5). Would not apply if: there is no second reviewer available, in which case state that the check is unreviewed.
- Introduce practices one at a time and only as needed, not all at once; this argues against growing the check system faster than the product. Rests on: incremental introduction (p. 5), not everything to the most exacting standards (p. 1). Would not apply if: a practice is required by an observed failure.
- For the legacy C++ DLL, use the original unpatched build as a test oracle: run identical seeded games on both and compare outputs where the patch should not change behaviour. Rests on: 6b prototype as test oracle (p. 4), regression tests (p. 4). Would not apply if: the harness is not deterministic for a given seed.
