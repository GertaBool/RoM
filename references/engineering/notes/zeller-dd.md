## What it says
- p. 1 (Abstract): "The Delta Debugging algorithm generalizes and simplifies some failing test case to a minimal test case that still produces the failure; it also isolates the difference between a passing and a failing test case." -- the two tasks of the paper.
- p. 1 (Abstract): "In a case study, the Mozilla web browser crashed after 95 user actions." -- the prototype simplified this to 3 relevant actions, and 896 lines of HTML to the one line causing the failure.
- p. 1 (Abstract): "The case study required 139 automated test runs, or 35 minutes on a 500 MHz PC." -- the stated cost.
- p. 1 (I. Introduction): "The first step in processing any bug report is simplification, that is, eliminating all details that are irrelevant for producing the failure." -- a simplified report also subsumes others differing only in irrelevant details.
- p. 1 (I. Introduction): "In July 1999, Bugzilla, the Mozilla bug database, listed more than 370 open bug reports" -- not even simplified; the Mozilla BugAThon asked volunteers to turn them into minimal test cases.
- p. 1 (I. Introduction): "A bug report should be as specific as possible" -- so the engineer can recreate the context; on the other hand a test case should be as simple as possible, because a minimal test case implies a most general context.
- p. 1 (I. Introduction): "The striking thing about test case simplification is that no one so far has thought to automate this task." -- textbooks describe binary search assuming manual tests.
- p. 1 (I. Introduction): "It stops when a minimal test case is reached, where removing any single input entity would cause the failure to disappear." -- the ddmin algorithm simplifies a failing test case by successive testing.
- p. 1 (I. Introduction): "Each part of this skeleton is relevant for reproducing the crash." -- the flight-test analogy; for programs such repeated tests come "at a far lesser cost."
- p. 1 (I. Introduction): "In the case where a passing test case exists as well, it is generally more efficient to isolate the failure-inducing difference between a failing and a passing test case." -- this is the general algorithm dd, a generalisation of ddmin.
- p. 2 (I. Introduction): "dd also maximizes the passing HTML input until a minimal failure-inducing difference is obtained." -- in the example the first character of the SELECT tag, after only seven tests.
- p. 2 (I. Introduction): "Delta Debugging can be applied to all circumstances that in any way affect the program" -- not limited to HTML, characters, or program input.
- p. 2 (I. Introduction): "Delta Debugging is fully automatic: whenever some regression test fails, an additional Delta Debugging run automatically determines the failure-inducing circumstances." -- intended use.
- p. 2 (I. Introduction): "we have shown how Delta Debugging is applied to isolate failure-inducing code changes" -- earlier work [3]; this paper concentrates on program input.

## Readings for our work
- Inference: when a harness game, a save or a log triggers a failure or an odd AI behaviour, reduce it automatically before analysing: decompose it (e.g. players, turns, options, log lines) and run ddmin with a scripted test that returns pass, fail or unresolved; report the reduced case and the number of tests. Rests on: Abstract; I. Introduction (simplification first); II.C three outcomes; III.B. Would not apply if: the failure cannot be reproduced by a script (the paper's premise is an automated test).
- Inference: a test predicate must distinguish the original failure from other failures (e.g. by the crash backtrace or the exact assertion), returning unresolved otherwise, or the reduction will converge on a different bug. Check: the reduced case reproduces the same signature as the original. Rests on: IV.D The Precision Effect. Would not apply if: any failure of the kind is acceptable (e.g. all crashes must be fixed anyway, as the authors note).
- Inference: when there is a passing and a failing version (DLL before and after a patch, two harness configurations), isolating the difference (dd) is far cheaper than minimising the failing case and gives the change to inspect; this is the same idea as git bisect on commits but applies to unordered sets of changes such as option sets or the hunks of one large patch. Rests on: V.A Isolation Illustrated; V.C; II.B (DIFF hunks as changes); I. Introduction (earlier work on code changes). Would not apply if: changes interact non-monotonically (VIII. Undoing changes), when the result may mislead.
- Inference: the test predicate needs a time bound and a deterministic outcome; noisy outcomes (as in seeded A/B games) make tests unresolved or wrong, so use fixed seeds and treat timeouts as unresolved. Rests on: footnote 10 (time bound); Table II note on outcomes not reproducible deterministically (UNITS t11, t12, only as table text); V.C (unresolved outcomes cost tests). Would not apply if: the effect is deterministic for a fixed seed.
- Inference: a claim that some circumstance causes an AI outcome needs an experiment that alters it and makes the effect disappear; reading code or logs can only rule causes out. This matches our rule that AI changes are judged by experiment. Rests on: VIII. Program analysis (analysis disproves, testing proves); IX. Conclusion. Would not apply if: the effect follows from a formula and is computed (our rule 9 exception), where the formula is the proof.
- Inference: structure-aware decomposition (lines before characters; grammar units) reduces tests; for CRLF C++ files or XML records, split by lines or records, not bytes, and never let the reduction produce edits beyond the minimal difference. Rests on: III.C (knowledge of input structure); IV.B hierarchical approach; VIII. Domain-specific methods. Would not apply if: the failure lies inside a token (then finer granularity is needed).
- Inference: the reported cost figures (139 tests or 35 minutes; 731 tests and 34 seconds; 36,000 tests of 0.1 s taking 1 hour) are from 2002 hardware and these programs; for our harness, estimate tests times per-game duration before choosing ddmin over dd. Rests on: Abstract; IV.A; V. Would not apply if: individual tests are fast enough that the quadratic worst case is affordable.
