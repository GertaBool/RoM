# D. Sculley, Gary Holt, Daniel Golovin, Eugene Davydov, Todd Phillips, Dietmar Ebner, Vinay Chaudhary, Michael Young, Jean-François Crespo, Dan Dennison, Hidden Technical Debt in Machine Learning Systems (NIPS, 2015)
Source: lit3/sculley-debt/doc.txt. Read: lines 1-458 (all, including references).

## What it says
- p. 1 (Abstract): "it is common to incur massive ongoing maintenance costs in real-world ML systems" -- the central claim; the listed risk factors are boundary erosion, entanglement, hidden feedback loops, undeclared consumers, data dependencies, configuration issues, changes in the external world and system-level anti-patterns.
- p. 1 (1 Introduction): "developing and deploying ML systems is relatively fast and cheap, but maintaining them over time is difficult and expensive."
- p. 1 (1 Introduction): "Not all debt is bad, but all debt needs to be serviced." -- technical debt is Cunningham's 1992 metaphor for long-term costs of moving quickly.
- p. 1 (1 Introduction): "Technical debt may be paid down by refactoring code, improving unit tests, deleting dead code, reducing dependencies, tightening APIs, and improving documentation" -- the goal of paying it down is "not to add new functionality, but to enable future improvements".
- p. 1 (1 Introduction): "Deferring such payments results in compounding costs. Hidden debt is dangerous because it compounds silently."
- p. 1 (1 Introduction): "This debt may be difficult to detect because it exists at the system level rather than the code level." -- and code-level methods of paying debt are "not sufficient to address ML-specific technical debt at the system level."
- p. 1 (1 Introduction): "This paper does not offer novel ML algorithms" -- stated limit: the aim is awareness of long-term tradeoffs, focused on system-level interactions and interfaces.
- p. 2 (2 Complex Models Erode Boundaries): "strong abstraction boundaries using encapsulation and modular design help create maintainable code" -- but for ML "it is difficult to enforce strict abstraction boundaries" because ML is used where behaviour cannot be expressed in logic without external data.
- p. 2 (2, Entanglement): "We refer to this here as the CACE principle: Changing Anything Changes Everything." -- changing one input's distribution, or adding or removing a feature, can change the weights of all others; CACE also applies to hyper-parameters, sampling, thresholds and data selection.
- p. 2 (2, Entanglement): "improving an individual component model may actually make the system accuracy worse" -- for ensembles whose value rests on uncorrelated errors; mitigations offered are isolating models and detecting changes in prediction behaviour, with slice-by-slice metrics.
- p. 2 (2, Correction Cascades): "a correction cascade can create an improvement deadlock" -- a model learned on top of another model as a correction creates a dependency; mitigations are to learn the corrections inside the original model or accept a separate model.
- p. 2 (2, Undeclared Consumers): "some of these consumers may be undeclared, silently using the output of a given model as an input to another system" -- called visibility debt in classical software engineering.
- p. 2 (2, Undeclared Consumers): "this tight coupling can radically increase the cost and difficulty of making any changes to ma at all, even if they are improvements."
- p. 3 (2, Undeclared Consumers): "In the absence of barriers, engineers will naturally use the most convenient signal at hand, especially when working against deadline pressures." -- detection needs access restrictions or strict SLAs.
- p. 3 (3 Data Dependencies Cost More than Code Dependencies): "Code dependencies can be identified via static analysis by compilers and linkers." -- without such tooling for data, large dependency chains are easy to build and hard to untangle.
- p. 3 (3, Unstable Data Dependencies): even improvements "to input signals may have arbitrary detrimental effects in the consuming system" -- example: a model fitted to a mis-calibrated signal is disrupted when the signal is silently corrected.
- p. 3 (3, Unstable Data Dependencies): "One common mitigation strategy for unstable data dependencies is to create a versioned copy of a given signal." -- with the stated costs of staleness and of maintaining several versions.
- p. 3 (3, Underutilized Data Dependencies): "underutilized data dependencies are input signals that provide little incremental modeling benefit" -- they make the system vulnerable to change; the old-and-new product number example ends with deleted code breaking the model a year later.
- p. 3 (3, Underutilized Data Dependencies): the ways they creep in are Legacy Features ("Over time, F is made redundant by new features but this goes undetected."), Bundled Features, epsilon-Features and Correlated Features.
- p. 3 (3, Underutilized Data Dependencies): "Underutilized dependencies can be detected via exhaustive leave-one-feature-out evaluations. These should be run regularly to identify and remove unnecessary features."
- p. 4 (Figure 1): "Only a small fraction of real-world ML systems is composed of the ML code" -- the surrounding infrastructure is vast and complex.
- p. 4 (3, Static Analysis of Data Dependencies): "Automated checks can then be run to ensure that all dependencies have the appropriate annotations, and dependency trees can be fully resolved." -- the cited feature management system annotates data sources and features; this makes migration and deletion safer.
- p. 4 (4 Feedback Loops): "This leads to a form of analysis debt, in which it is difficult to predict the behavior of a given model before it is released." -- loops are harder to detect when they occur gradually.
- p. 4 (4, Direct Feedback Loops): "A model may directly influence the selection of its own future training data." -- mitigations: some randomization, or isolating parts of the data from the model's influence.
- p. 4 (4, Hidden Feedback Loops): "hidden feedback loops, in which two systems influence each other indirectly through the world." -- examples: two components of one web page; two stock-market models of different firms.
- p. 4 (5 ML-System Anti-Patterns): "only a tiny fraction of the code in many ML systems is actually devoted to learning or prediction" -- the rest is called plumbing.
- p. 5 (5, Glue Code): "Glue code is costly in the long term because it tends to freeze a system to the peculiarities of a specific package" -- a mature system "might end up being (at most) 5% machine learning code and (at least) 95% glue code"; the strategy offered is to wrap black-box packages into common APIs.
- p. 5 (5, Pipeline Jungles): "become a jungle of scrapes, joins, and sampling steps, often with intermediate files output." -- testing them often requires expensive end-to-end integration tests.
- p. 5 (5, Pipeline Jungles): "Pipeline jungles can only be avoided by thinking holistically about data collection and feature extraction." -- a clean-slate redesign is a major investment that can dramatically reduce ongoing costs.
- p. 5 (5, Pipeline Jungles): "A hybrid research approach where engineers and researchers are embedded together on the same teams" -- proposed for glue code and pipeline jungles rooted in separated research and engineering roles.
- p. 5 (5, Dead Experimental Codepaths): "implementing experimental codepaths as conditional branches within the main production code" -- cheap per change, but accumulates debt, backward-compatibility burden and an exponential increase in cyclomatic complexity.
- p. 5 (5, Dead Experimental Codepaths): "Knight Capital’s system losing $465 million in 45 minutes, apparently because of unexpected behavior from obsolete experimental codepaths" -- the evidence given.
- p. 5 (5, Dead Experimental Codepaths): "it is often beneficial to periodically reexamine each experimental branch to see what can be ripped out." -- often only a small subset of branches is used.
- p. 5 (5, Abstraction Debt): "there is a distinct lack of strong abstractions to support ML systems." -- compared with the relational database; Map-Reduce named a poor abstraction for iterative ML.
- p. 6 (5, Common Smells): "We identify a few ML system smells, not hard-and-fast rules, but as subjective indicators." -- stated limit on the smells.
- p. 6 (5, Plain-Old-Data Type Smell): "a model parameter should know if it is a log-odds multiplier or a decision threshold" -- rich information is too often encoded as raw floats and integers.
- p. 6 (5, Multiple-Language Smell): "using multiple languages often increases the cost of effective testing and can increase the difficulty of transferring ownership to other individuals."
- p. 6 (5, Prototype Smell): "there is a significant danger that time pressures may encourage a prototyping system to be used as a production solution." -- also: "results found at small scale rarely reflect the reality at full scale."
- p. 6 (6 Configuration Debt): "both researchers and engineers may treat configuration (and extension of configuration) as an afterthought." -- in a mature system lines of configuration can far exceed lines of code, and "Each configuration line has a potential for mistakes."
- p. 6 (6 Configuration Debt): "It should be easy to specify a configuration as a small change from a previous configuration." -- first of the stated principles; the others: hard to make manual errors, easy to see the difference between two configurations, easy to assert and verify basic facts, possible to detect unused settings.
- p. 6 (6 Configuration Debt): "Configurations should undergo a full code review and be checked into a repository."
- p. 7 (7, Fixed Thresholds in Dynamic Systems): "if a model updates on new data, the old manually set threshold may be invalid." -- the cited mitigation learns thresholds on held-out validation data.
- p. 7 (7, Monitoring and Testing): "in the face of a changing world such tests are not sufficient to provide evidence that a system is working as intended." -- live monitoring with automated response is called critical.
- p. 7 (7, Prediction Bias): "the distribution of predicted labels is equal to the distribution of observed labels." -- the authors state it "is by no means a comprehensive test" since a null model passes it, but a useful diagnostic, sliceable for alerting.
- p. 7 (7, Action Limits): "These limits should be broad enough not to trigger spuriously." -- hitting a limit should fire alerts and trigger manual investigation.
- p. 7 (7, Up-Stream Producers): "These up-stream processes should be thoroughly monitored, tested, and routinely meet a service level objective" -- and alerts must propagate in both directions.
- p. 7 (8, Data Testing Debt): "If data replaces code in ML systems, and code should be tested, then it seems clear that some amount of testing of input data is critical" -- basic sanity checks and tests that monitor input distributions.
- p. 8 (8, Reproducibility Debt): "it is important that we can re-run experiments and get similar results" -- made difficult by randomized algorithms, parallel non-determinism, initial conditions and external interactions.
- p. 8 (8, Process Management Debt): "An important system-level smell to avoid are common processes with many manual steps."
- p. 8 (8, Cultural Debt): "reward deletion of features, reduction of complexity, improvements in reproducibility, stability, and monitoring to the same degree that improvements in accuracy are valued."
- p. 8 (9 Conclusions): "it unfortunately does not provide a strict metric that can be tracked over time." -- stated limit of the metaphor; "Simply noting that a team is still able to move quickly is not in itself evidence of low debt".
- p. 8 (9 Conclusions): the questions offered include "What is the transitive closure of all data dependencies?" and "How precisely can the impact of a new change to the system be measured?" and "Does improving one model or signal degrade others?"
- p. 8 (9 Conclusions): "Research solutions that provide a tiny accuracy benefit at the cost of massive increases in system complexity are rarely wise practice."
- p. 8 (9 Conclusions): "Paying down ML-related technical debt requires a specific commitment, which can often only be achieved by a shift in team culture."

## Readings for our work
- Measure our own glue-to-product ratio: count lines in method/ checks, hooks and tooling against lines of analysis and AI-change code, per commit window, and treat growth of the former without growth of the latter as debt to pay down, not progress. Rests on: Figure 1 and the 5%/95% glue-code claim (p. 4-5), cultural debt rewarding deletion (p. 8). Would not apply if: the checks demonstrably prevent errors that cost more than they add, shown by recorded caught failures.
- Delete dead code paths and unused checks on a schedule: list each check or tool and its last caught failure; one that never fired or whose consumer is gone goes. Rests on: dead experimental codepaths and periodic re-examination (p. 5), underutilized dependencies (p. 3). Would not apply if: a check guards a rare but catastrophic failure that has a recorded precedent.
- Keep experimental AI variants in the DLL behind a single, removable switch per prediction, and remove the branch when the prediction is decided, rather than accumulating conditional branches in production code. Rests on: dead experimental codepaths and Knight Capital (p. 5), CACE (p. 2). Would not apply if: the variant is adopted, in which case it becomes the default and the switch is removed.
- Treat any table derived from game logs as a data dependency with declared consumers: each document template should name the registry entries and DuckDB views it reads, so a change to a view lists its consumers. Rests on: undeclared consumers (p. 2-3), static analysis of data dependencies (p. 4). Would not apply if: views are never reused across documents.
- Freeze and version the inputs of an experiment (DLL build, XML, harness seeds, opponents) and record the versions with each result; do not let a rebuilt DLL silently change the baseline. Rests on: unstable data dependencies and versioned copies (p. 3), reproducibility debt (p. 8). Would not apply if: the baseline is rebuilt and re-run in the same experiment.
- Harness and scenario configuration should be checked in, reviewed, expressed as small diffs from a named base configuration, and diffable between two runs. Rests on: configuration debt principles (p. 6). Would not apply if: configuration is fully derived from code with no hand-set options.
- When one AI change improves one metric, check the others: a change to one AI behaviour can shift unrelated outcomes, so judge on all essential variables, not only the targeted one. Rests on: CACE (p. 2), conclusion question on degrading others (p. 8). Would not apply if: the change is provably isolated, e.g. a formula effect computed without simulation.
- Add input-data sanity checks on the logs before analysis (row counts per turn, players, value ranges) instead of trusting the pipeline. Rests on: data testing debt (p. 7), pipeline jungles (p. 5). Would not apply if: log format is validated at write time by the DLL.
