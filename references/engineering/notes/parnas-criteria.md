# D.L. Parnas, On the Criteria To Be Used in Decomposing Systems into Modules (Communications of the ACM 15(12), December 1972)
Source: lit3/parnas-criteria/doc.txt. Read: lines 1-598 (all).

## What it says
- p. 1 (abstract): "This paper discusses modularization as a mechanism for improving the flexibility and comprehensibility of a system while allowing the shortening of its development time."
- p. 1 (abstract): "dependent upon the criteria used in dividing the system into modules." -- the effectiveness of a modularization depends on its criteria; a conventional and an unconventional decomposition are compared.
- p. 1 (abstract): "if implemented with the conventional assumption that a module consists of one or more subroutines, will be less efficient in most cases." -- stated limit of the unconventional decomposition; an alternative implementation is sketched.
- p. 1 (introduction): "Usually nothing is said about the criteria to be used in dividing the system into modules." -- quoted textbook (Gauthier and Pont) describes the benefits of modularity without saying how to divide.
- p. 1 (a brief status report): "allow one module to be written with little knowledge of the code in another module" -- and to reassemble and replace modules without reassembling the whole system; the problem systems are already highly modularized with such techniques.
- p. 2 (expected benefits): "development time should be shortened because separate groups would work on each module with little need for communication" -- the managerial benefit.
- p. 2 (expected benefits): "it should be possible to make drastic changes to one module without a need to change others" -- product flexibility; and comprehensibility: "it should be possible to study the system one module at a time."
- p. 2 (what is modularization?): "to be a responsibility assignment rather than a subprogram." -- the definition of module used in the paper.
- p. 2 (what is modularization?): "The modularizations include the design decisions which must be made before the work on independent modules can begin." -- system-level decisions are those affecting more than one module.
- p. 2 (example system 1): "The KWIC index system accepts an ordered set of lines, each line is an ordered set of words, and each word is an ordered set of characters." -- it outputs all circular shifts of all lines in alphabetical order.
- p. 2 (example system 1): "such a system could be produced by a good programmer within a week or two." -- stated limit: none of the difficulties motivating modular programming matter for this system; it is treated as if it were large.
- p. 2 (modularization 1): "The characters are packed four to a word, and an otherwise unused character is used to indicate the end of a word." -- modules are input, circular shift, alphabetizing, output and master control, communicating through arrays in core.
- p. 2 (modularization 1): "All of the interfaces between the four modules must be specified before work could begin." -- defining documents would include core formats, pointer conventions and calling conventions.
- p. 2 (modularization 1): "Experiments on a small scale indicate that this is approximately the decomposition which would be proposed by most programmers for the task specified."
- pp. 2-3 (modularization 2): "There are certain restrictions in the way that these routines may be called; if these restrictions are violated the routines" -- line storage offers functions such as CHAR, SETCHAR and WORDS, and traps misuse to an error routine provided by its users.
- p. 3 (modularization 2): "The module creates the impression that we have created a line holder containing not all of the lines but all of the circular shifts of the lines." -- the circular shifter; the alphabetizer offers ALPH and ITH.
- p. 3 (comparison, general): "Our discussion is about two different ways of cutting up what may be the same object." -- both may share data representations and algorithms; they differ in work assignments and interfaces.
- p. 3 (comparison, general): "substantially different even if identical in the runnable representation." -- other representations are used for changing, documenting and understanding.
- p. 3 (changeability): "There are a number of design decisions which are questionable and likely to change under many circumstances." -- listed: input format, storing all lines in core, packing four characters to a word, an index for shifts rather than storing them, alphabetizing once.
- p. 3 (changeability): "For the first decomposition the second change would result in changes in every module!" -- the same for the third; the first change is confined to one module in both.
- p. 3 (changeability): "Knowledge of the exact way that the lines are stored is entirely hidden from all but module 1." -- a symbol table module used inside line storage was invisible to the rest of the system.
- pp. 3-4 (changeability): "designed so that a user could not detect when the alphabetization was actually done." -- so the fifth change needs no other module changed, while in the first decomposition output expects the index to be complete.
- p. 4 (independent development): "The development of those formats will be a major part of the module development and that part must be a joint effort among the several development groups." -- in the second modularization interfaces are function names and parameter numbers and types, so independent work can begin earlier.
- p. 4 (comprehensibility): "The system will only be comprehensible as a whole." -- for the first modularization; stated as the author's subjective judgment that this is not true of the second.
- p. 4 (the criteria): "the criterion used was to make each major step in the processing a module." -- the flowchart approach.
- p. 4 (the criteria): "The flowchart was a useful abstraction for systems with on the order of 5,000-10,000 instructions" -- beyond that it does not appear sufficient.
- p. 4 (the criteria): "Every module in the second decomposition is characterized by its knowledge of a design decision which it hides from all others." -- the criterion is information hiding.
- p. 4 (the criteria): "Its interface or definition was chosen to reveal as little as possible about its inner workings."
- p. 4 (improvement in circular shift module): "By prescribing the order for the shifts we have given more information than necessary" -- this restricted the class of systems buildable without changing definitions; the author classifies it as a design error.
- p. 4 (specific decompositions): "A data structure, its internal linkings, accessing procedures and modifying procedures are part of a single module." -- not shared by many modules as is conventional.
- p. 4 (specific decompositions): "The sequence of instructions necessary to call a given routine and the routine itself are part of the same module." -- essential in assembly language, where calling sequences vary.
- p. 4 (specific decompositions): "Because design evolution forces frequent changes on control block formats such a decision often proves extremely costly." -- control block formats should be hidden in a control block module.
- pp. 4-5 (specific decompositions): "Character codes, alphabetic orderings, and similar data should be hidden in a module for greatest flexibility." -- and the processing sequence should be hidden in a single module as far as practical.
- p. 5 (efficiency and implementation): "If we are not careful the second decomposition will prove to be much less efficient than the first." -- because of repeated switching between modules through procedure calls.
- p. 5 (efficiency and implementation): "will require a tool by means of which programs may be written as if the functions were subroutines, but assembled by whatever implementation is appropriate."
- p. 5 (efficiency and implementation): "must be maintained in the machine together with a program performing mapping between them." -- the several representations of the program.
- p. 5 (compiler and interpretor): "we discovered that our decomposition was valid for a pure compiler and several varieties of interpretors for the language."
- p. 5 (compiler and interpretor): "the order in time in which processing is expected to take place should not be used in making the decomposition into modules." -- and careful decomposition can carry work over between projects.
- p. 5 (hierarchical structure): "We have a hierarchical structure if a certain relation may be defined between the modules or programs and that relation is a partial ordering." -- the relation is uses or depends upon, better defined between programs than modules.
- p. 5 (hierarchical structure): "we are able to cut off the upper levels and still have a usable and useful product." -- the second benefit of the partial ordering; the first is that parts are simplified by using lower levels.
- p. 5 (hierarchical structure): "it much harder to remove portions of the system" -- if low-level modules used high-level ones there would be no hierarchy.
- p. 6 (hierarchical structure): "are two desirable but independent properties of a system structure." -- hierarchical structure and clean decomposition.
- p. 6 (conclusion): "it is almost always incorrect to begin the decomposition of a system into modules on the basis of a flowchart."
- p. 6 (conclusion): "We propose instead that one begins with a list of difficult design decisions or design decisions which are likely to change." -- each module then hides such a decision from the others.
- p. 6 (conclusion): "we must abandon the assumption that a module is one or more subroutines" -- to achieve efficiency, subroutines may be assembled from code of various modules.

## Readings for our work
- Our analysis tools are naturally split by processing step (parse save, load logs, query, render), which is the flowchart criterion the paper argues against. Instead list the decisions likely to change (log format of the mod, DuckDB schema, unit list in figlib, template syntax) and give each one module that alone knows it. Check: for each such decision, grep how many files depend on it; more than one is a leak. Rests on: changeability, the criteria, conclusion. Would not apply if: the tool is small enough to be written in a week or two and never changed (the paper's own stated limit).
- The figure registry is an interface: documents should depend on figure names and units, not on how figures are computed or stored. A template that reads a raw table directly bypasses it. Rests on: information hiding, reveal as little as possible. Would not apply if: the registry format itself is the stable public contract.
- Do not let interfaces promise more than needed (like the shift order). For checks and tools, specify only what callers rely on, so the implementation can be replaced. Rests on: improvement in circular shift module. Would not apply if: callers genuinely need the extra guarantee.
- Keep the method's dependency graph a partial order: checks (lower level) must not import analysis code (higher level), so the method can be cut off and reused or replaced. Check: an import graph of method/ and research/ has no edges from method/ to research/. Rests on: hierarchical structure. Would not apply if: a check is specific to one analysis by design.
- For DLL patches, a change confined to one module is the goal; when a patch has to touch many files for one decision, that decision is exposed in the legacy design, and the patch should say so rather than spread further. Rests on: changeability (changes in every module). Would not apply if: the change is a mechanical rename required by the compiler.
- Generated files are a second representation of the same program; they must be produced by the mapping program, never edited by hand. Rests on: several representations maintained together with a mapping program. Would not apply if: a generated file is deliberately forked and its generator retired.
