## What it says
- Introduction: "Dependency management—the management of networks of libraries, packages, and dependencies that we don’t control—is one of the least understood and most challenging problems in software engineering." -- definition and claim.
- Introduction: "Dependency management focuses on the problems that arise when changes are being made outside of your organization, without full access or visibility." -- contrast with source control, which covers the easier part.
- Introduction: "it is easy to construct scenarios in which your organization’s use of two dependencies becomes unsatisfiable at some point in time." -- the network view; footnote 1 lists language version, library version, hardware, OS, compiler flag and compiler version as possible requirements.
- Introduction: "Source control and dependency management are related issues separated by the question: “Does our organization control the development/update/management of this subproject?”" -- the dividing question.
- Introduction: "All else being equal, prefer source control problems over dependency-management problems." -- the author's "strongest single piece of advice"; redefine organization broadly where possible.
- Introduction: "We don’t have firsthand evidence of solutions that work well across organizations at scale." -- stated limit; the chapter is partly "a summary of what we know does not work".
- Why Is Dependency Management So Difficult?: "The trick isn’t just finding a way to manage one dependency—the trick is how to manage a network of dependencies and their changes over time." -- the problem formulation; "Over a long enough period, all of the nodes in that dependency network will have new versions".
- Conflicting Requirements and Diamond Dependencies: "what happens when two nodes in the dependency network have conflicting requirements, and your organization depends on them both?" -- the central problem.
- Conflicting Requirements and Diamond Dependencies: "most of these conflicting requirements problems are isomorphic to “add a (hidden) node to the dependency graph representing this requirement.”" -- compiler version etc. treated as hidden nodes.
- Conflicting Requirements and Diamond Dependencies: "If liba depends on the new libbase version and libb depends on the old version, there’s no general way for libuser (aka your code) to put everything together." -- the diamond; it requires at least three layers.
- Conflicting Requirements and Diamond Dependencies: "C++ has nearly zero tolerance for diamond dependencies in a normal build, and they are very likely to trigger arbitrary bugs and undefined behavior (UB) as a result of a clear violation of C++’s One Definition Rule." -- language-specific tolerance.
- Conflicting Requirements and Diamond Dependencies: "if there are types that are passed around between dependencies, all bets are off." -- limits of renaming and shading workarounds, including hiding symbols in a DLL.
- Conflicting Requirements and Diamond Dependencies: "the only easy answer is to skip forward or backward in versions for those dependencies to find something compatible." -- otherwise local patching, made hard because the discoverer probably does not know the cause.
- Conflicting Requirements and Diamond Dependencies: "How do we avoid conflicting requirements while still allowing change among noncoordinating groups?" -- the question dependency management reduces to.
- Importing Dependencies: "if your external dependency satisfies the requirements for your programming task, you should use it." -- reuse is healthy, absent trojaned software.
- Compatibility Promises: "Just because you get to avoid a development cost doesn’t mean importing a dependency is the correct choice." -- ongoing maintenance costs; security, platforms and networks can force upgrades regardless of intent.
- Compatibility Promises: "We suggest that a dependency provider should be clearer about the answers to these questions." -- how much compatibility and evolution is assumed, how long releases are supported.
- C++: "For the C++ standard library, the model is one of nearly indefinite backward compatibility." -- includes ABI compatibility, upheld variably by platform; SD-8 lists permitted changes.
- Go: "The Go programming language explicitly promises source compatibility between most releases, but no binary compatibility." -- contrast.
- Abseil: "we won’t make a breaking API change without also providing an automated refactoring tool that will transform code from the old API to the new transparently." -- Abseil's limited API promise, no ABI promise; about 250 million lines of internal C++ depend on it.
- Abseil: "In practice, the project is new enough that we haven’t had to make any significant API breaking changes." -- stated limit of the evidence for the Abseil model.
- Boost: "this is purely a matter of what a project does or does not promise and prioritize." -- Boost makes no compatibility promise; it is an experimental proving ground.
- Boost (discussion): "these compatibility issues are software engineering issues, not programming issues." -- the difference between “I got it to work” and “this is working in a supported fashion.”
- Boost (discussion): "If you’re purely developing a solution for today with no need to ever update anything, it is perfectly reasonable to grab as many readily available dependencies as you like" -- valid only so long as nothing is ever upgraded.
- Considerations When Importing: "when we move from programming to software engineering, those dependencies become subtly more expensive, and there are a host of hidden costs and questions that need to be answered." -- the cost shift.
- Considerations When Importing: "Does the project have tests that you can run?" -- first of the listed questions; others include who provides it, what compatibility it aspires to, how long we will depend on it, how often it breaks, who will upgrade and how hard it will be.
- Considerations When Importing: "We can’t give a perfect formula for deciding when it’s cheaper in the long term to import versus reimplement; we fail at this ourselves, more often than not." -- stated limit.
- How Google Handles Importing Dependencies: "In short: we could do better." -- self-assessment.
- How Google Handles Importing Dependencies: "Most problems in dependency management stop being problems when you can see exactly how your code is being used and know exactly the impact of any given change." -- why most internal dependencies are a source control matter.
- How Google Handles Importing Dependencies: "make sure at least two engineers are signed up as OWNERS to maintain the package in the event that any maintenance is necessary." -- the third_party checklist (builds, no existing version, two owners).
- How Google Handles Importing Dependencies: "they might not necessarily notice growth in the transitive usage of their package." -- the Alice and Bob scenario: a demo dependency becomes critical infrastructure without signals to anyone.
- How Google Handles Importing Dependencies: "The more that the package remains stable, the more that we are likely to accrete Hyrum’s Law reliance on the particulars of the version that is checked into third_party." -- cost of not updating.
- How Google Handles Importing Dependencies: "the upgrade is extra difficult because it is covering many smaller releases covering the entire period between initial introduction of the package into third_party and the security disclosure." -- the forced, late upgrade with nobody practised.
- How Google Handles Importing Dependencies: "we need to make it easier (and more rewarding) to update regularly and more difficult for third_party packages to be orphaned and important at the same time." -- what the authors think is needed; "Our third_party policies don’t work for these unfortunately common scenarios."
- How Google Handles Importing Dependencies: "upstream projects that are not explicitly prioritizing stability are a risk." -- given a codebase lifespan of decades.
- Dependency Management, In Theory: "all software has bugs, some of those will be security critical, and some fraction of our dependencies will therefore be critical to update over a long enough period of time." -- the time constraint.
- Dependency Management, In Theory: "If it does so without assuming stability in dependency version or dependency fan-out, coordination or visibility between organizations, or significant compute resources, it’s a great solution." -- the criteria for good and great solutions.
- Dependency Management, In Theory: "nothing ever changes, semantic versioning, bundle everything that you need (coordinating not per project, but per distribution), or Live at Head." -- the four options.
- Nothing Changes: "Bug fixes are allowed only if no user code could be broken." -- the static model.
- Nothing Changes: "this is probably the right model for most new organizations." -- but "over a long enough time period, it is false, and there isn’t a clear indication of exactly how long you can pretend that it is legitimate."
- Nothing Changes: "a single upgrade can in theory become a forced update to your entire dependency network." -- no early warning for forcing issues.
- Semantic Versioning: "a changed major number indicates a change to an existing API that can break existing usage, a changed minor number indicates purely added functionality that should not break existing usage" -- SemVer definition; patch is reserved for low-risk implementation details and bug fixes.
- Semantic Versioning: "Version-satisfiability solvers for SemVer are very much akin to SAT-solvers in logic and algorithms research" -- footnote 7: SemVer constraints over a network are NP-complete.
- Semantic Versioning: "SemVer and its SAT-solvers aren’t in any way promising that there exists a solution to a given set of dependency constraints." -- no satisfying assignment is called dependency hell.
- Bundled Distribution Models: "Distributors are the engineers responsible for proposing a set of versions to bundle together, testing those to find bugs in that dependency tree, and resolving any issues." -- the bundled model, as in Linux distributions.
- Bundled Distribution Models: "This is effectively the same as changing a dependency network into a single aggregated dependency and giving that a version number." -- works so long as you rely on only one distribution.
- Live at Head: "always depend on the current version of everything, and never change anything in a way in which it would be difficult for your dependents to adapt." -- the model; an extension of trunk-based development.
- Live at Head: "A change that (unintentionally) alters API or behavior will in general be caught by CI on downstream dependencies, and thus should not be committed." -- breaks only after dependents are updated or an automated tool is provided.
- Live at Head: "tests and CI systems are used to test against visible dependents to determine experimentally how safe a change is." -- instead of a SemVer judgement.
- Live at Head: "API consumers are incentivized to keep their tests working so as not to be labeled as a low-signal test and potentially skipped" -- the assumed incentives; it works better with visible than with closed dependents.
- The Limitations of SemVer: "is largely unproven at scale." -- of Live at Head; SemVer is the de facto standard.
- The Limitations of SemVer: "Fundamentally, you can’t prove anything about compatibility when only considering the source API; you have to know with which things you are asking about compatibility." -- the core critique.
- The Limitations of SemVer: "We’re building all of our version-satisfaction logic on top of a shaky foundation, treating estimates and self-attestation as absolute." -- SemVer numbers are maintainer estimates.
- The Limitations of SemVer: "SemVer can (and does) fail us by both overconstraining and underprotecting us." -- the two failure modes.
- SemVer Might Overconstrain: "only Bar changed, and that was unused." -- the Foo and Bar example: a major bump blocks a combination that would work.
- SemVer Might Overpromise: "how do we characterize a change that alters the format of our logging output?" -- examples of non-API changes that still break users.
- SemVer Might Overpromise: "With a sufficient number of users, every observable behavior of your system will be depended upon by someone." -- Hyrum's Law as quoted.
- SemVer Might Overpromise: "there are changes that are theoretically breaking but safe in practice (removing an unused API). There are also changes that are theoretically safe but break client code in practice" -- the term breaking change is misleading.
- SemVer Might Overpromise: "A change in isolation isn’t breaking or nonbreaking—that statement can be evaluated only in the context of how it is being used." -- the evaluation needs knowledge of downstream use.
- SemVer Might Overpromise: "you might have either build errors or runtime bugs, with no theoretical upper bound on their severity." -- consequence of a wrong solver result.
- Motivations: "the maintainers bear a tiny fraction of the cost of the resulting version bump." -- incentive problem; most users are indirect.
- Motivations: "projects should publish clear statements of intent with respect to compatibility, usage, and breaking changes." -- recommendation; Go and Clojure treat a major bump as a new package.
- Motivations: "discerning whether there are meaningful and intentional semantic changes is computationally infeasible." -- human judgement decides bumps; with thousands of dependencies, "be prepared for some amount of chaos simply from human error."
- Minimum Version Selection: "MVS makes the opposite choice: when liba’s specification requires libbase ≥1.7, we’ll try libbase 1.7 directly, even if a 1.8 is available." -- Russ Cox, 2018.
- Minimum Version Selection: "Absent accurate input constraints derived from 100% accurate prediction of the future, it’s best to make the smallest jump forward possible." -- smaller steps are safer, like committing an hour of work rather than a year.
- Minimum Version Selection: "Unfortunately, we haven’t found a good way to empirically verify that idea." -- stated limit; the authors still believe MVS is an improvement.
- So, Does SemVer Work?: "When you have only a few carefully chosen and well-maintained dependencies in your dependency graph, SemVer can be a perfectly suitable solution." -- conditions: accurate providers, fine-grained dependencies, usage within expected usage.
- So, Does SemVer Work?: "it is unlikely that you can have any of those three properties at scale and keep them working constantly over time." -- failures appear as false positives and false negatives.
- Dependency Management with Infinite Resources: "part of SemVer’s effective dominance is that we’re choosing to ignore information that is theoretically available to us." -- downstream usage is visible within one organisation or in OSS.
- Dependency Management with Infinite Resources: "With a sufficiently large number of such tests, we have at least a statistical argument that the change is safe in the practical Hyrum’s-Law sense." -- evidence instead of estimates.
- Dependency Management with Infinite Resources: "If we consider the goal to be more in line with “risk mitigation,” a statistical argument becomes a more appealing (and cost-effective) approach." -- prioritise tests in heavily used, well-maintained, good-signal dependencies.
- Dependency Management with Infinite Resources: "a pure refactoring change that modifies only internal APIs might be assumed to be low risk and justify running tests only in our own project" -- testing scaled to the kind of change; removing a deprecated interface may need as much testing as affordable.
- Dependency Management with Infinite Resources: "A proposed change that breaks a project that has a longstanding history of tests continuing to pass gives us a different form of evidence than a breakage in a project that was only added recently" -- history and reputation in CI; obstacles listed include missing tests, unknown reverse edges, limited compute, pinned versions.
- Dependency Management with Infinite Resources: "the model of dependency management given infinite resources is effectively that of the Live at Head model." -- conclusion of the thought experiment.
- Exporting Dependencies: "Given time, all forks will become expensive." -- the second way releasing can be a loss; the first is reputation.
- Example: open sourcing gflags: "the gflags project was doomed to be either a “throw over the wall” release or a disconnected fork." -- because large-scale refactoring was not yet possible and contributions could not flow back.
- Example: open sourcing gflags: "Given that it was no specific team’s job, and nobody could say why it was important, it isn’t surprising that we basically let that project rot externally." -- loss of ownership.
- Example: open sourcing gflags: "Don’t release things without a plan (and a mandate) to support it for the long term." -- lesson.
- Example: open sourcing gflags: "a tiny handful of projects were relying on unpromised and unexpected things." -- an optimization worth thousands of CPUs was delayed.
- Case Study: AppEngine: "we effectively tied “code that builds with the current C++ compiler” to “code that uses the updated Python version”" -- coupled upgrades; customers could not or would not update.
- Case Study: AppEngine: "every piece of C++ code in the transitive closure of dependencies from AppEngine had to be compatible with the older compiler and standard library versions" -- for almost three years.
- Case Study: AppEngine: "external users of an API cost a lot more to maintain than internal ones." -- conclusion; "externally shared dependencies are often much more expensive to modify over time."
- Conclusion: "SemVer presupposes that we can a priori predict the severity of a change, in the absence of knowledge of how the API in question is being consumed: Hyrum’s Law informs us otherwise." -- summary.
- Conclusion: "maintainer-provided estimates of compatibility (SemVer version numbers) are dropped in favor of experience-driven evidence: running the tests of affected downstream packages." -- the hoped-for future.
- TL;DRs: "Adding a dependency isn’t free for a software engineering project" -- also "A dependency is a contract" and "testing and CI provide actual evidence of whether a new set of versions work together."
- TL;DRs: "Providing a dependency isn’t free: “throw it over the wall and forget” can cost you reputation and become a challenge for compatibility." -- export side.
- Footnote 12: "it would still be difficult to algorithmically separate “This is a behavioral change” from “This is a bug fix to a behavior that wasn’t intended/promised.”" -- limit even with ubiquitous tests.

## Readings for our work
- Reading (inference): the DLL lives in a separate GitLab repository we do not control, so our relation to it is dependency management, not source control; pin the exact upstream commit each patch is made against, record it with the patch, and rebase in small steps rather than after a long gap. Rests on: the dividing question (control of the subproject); the third_party upgrade covering many releases at once; MVS smallest jump forward. Would not apply if: we own the GitLab repository and can see every change made there.
- Reading (inference): the toolchain (MSVC 2003 under Wine, its standard library, CRLF conventions) is a hidden node of the dependency graph and should be recorded and checked like a dependency, for example a script that prints compiler version and fails the build if it changes. Rests on: conflicting requirements isomorphic to a hidden node; footnote 1 on compiler version and flags; AppEngine tying compiler and runtime upgrades. Would not apply if: the build environment is fixed in an image whose identity is already verified per build.
- Reading (inference): judge whether a DLL patch is safe by evidence (seeded harness runs and build) rather than by our own estimate that it is a small or internal change; scale testing to the kind of change. Rests on: SemVer estimates vs experience-driven evidence; a change is breaking only in the context of its use; pure internal refactorings justify less testing, behaviour changes as much as affordable. Would not apply if: the change is provably identical in compiled output.
- Reading (inference): observable but unpromised behaviour of the game (log formats, ordering of output) will be depended on by our parsers; our DuckDB loaders should state which log fields and orders they rely on, and a patch that changes log output should be treated as a breaking change for our tools. Rests on: Hyrum's Law quote; logging-format and unordered-stream examples; gflags common subset breaking. Would not apply if: the parsers validate the log schema and fail loudly on drift.
- Reading (inference): in C++ two definitions of the same thing break silently; patches should not introduce a second copy of a header or type into the DLL build (for example, a vendored helper that shadows an existing one). Rests on: C++ nearly zero tolerance for diamonds, ODR violation, UB. Would not apply if: the duplicate is isolated in its own DLL with no shared types.
- Reading (inference): every Python dependency we add to the analysis tools should pass the import questions (tests we can run, who maintains it, who upgrades) and be pinned; prefer the standard library where the function is small. Rests on: Considerations When Importing list; Adding a dependency isn't free. Would not apply if: the dependency is used only in a throwaway script never re-run.
- Reading (inference): merge requests we deliver upstream are exported code; deliver only what we will support, and avoid forking the DLL in our repository, since forks diverge and become expensive. Rests on: all forks become expensive; gflags rot; don't release without a plan to support. Would not apply if: the upstream maintainers take ownership of the patch once merged.
- Reading (inference): a check is evidence only if its history is good; a harness test or check that has failed for unrelated reasons should be treated as low-signal until stable, and its failures recorded rather than ignored. Rests on: history and reputation in CI; low-signal tests skipped. Would not apply if: every check is deterministic.
