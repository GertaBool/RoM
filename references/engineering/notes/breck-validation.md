# Eric Breck, Neoklis Polyzotis, Sudip Roy, Steven Euijong Whang, Martin Zinkevich, Data Validation for Machine Learning (Proceedings of the 2nd SysML Conference, Palo Alto, CA, USA, 2019)

## What it says
- p. 1 (Abstract): "errors in the input data can nullify any benefits on speed and accuracy for training and inference." -- the argument for a data-centric approach that "treats training and serving data as an important production asset".
- p. 1 (Abstract): "It is used by hundreds of product teams use it to continuously monitor and validate several petabytes of production data per day." -- deployed as part of TFX at Google.
- p. 1 (Abstract): the stated benefits from deployment: "early detection of errors, model-quality wins from using better data, savings in engineering hours to debug problems".
- p. 1 (1 Introduction): "Irrespective of the ML algorithms used, data errors can adversely affect the quality of the generated model." -- and when predictions are logged and reused for training, feedback loops amplify small errors.
- p. 1 (1 Introduction): "it is imperative to catch data errors early, before they propagate through these complex loops and taint more of the pipeline’s state."
- p. 1 (1 Introduction): "any attempt to debug and understand the output of the model must be grounded on the assumption that the data is adequately clean." -- hence data should be "a first-class citizen in ML pipelines".
- p. 1 (1 Introduction): "Data validation is neither a new problem nor unique to ML" -- solutions are borrowed from database systems but must be rethought for ML.
- p. 2 (Example 1.1): "introduces a bug that pins the value of a specific int feature to -1 for some slice of the serving data" -- the model keeps predicting at lower accuracy, the bad serving data becomes training data, and "the data looks perfectly fine for the training code".
- p. 2 (1 Introduction): "A lack of visibility by the ML pipeline into this data generation logic except through side effects" -- data arrive in raw formats that strip semantic information, so there is little a-priori information to reason about errors.
- p. 2 (1 Introduction): "The example also illustrates a very common source of data errors in production: bugs in code." -- implications: errors have structure reflecting the faulty code, differ from data-cleaning errors, and fixing them requires code changes that are hard to automate.
- p. 2 (1 Introduction): "the data-validation system must generate reliable alerts with high precision, and provide enough context so that the on-call engineer can quickly identify the root cause"
- p. 2 (1 Introduction): "Our experience shows that on-calls tend to ignore alerts that are either spammy or not actionable, which can cause important errors to go unnoticed."
- p. 2 (1 Introduction): "it is important to rely on mechanisms specific to data validation rather than on detection of second-order effects." -- model-quality validation as a failsafe misses slice-specific errors when aggregate metrics still look okay.
- p. 2 (Our Contributions): "Hundreds of product teams use our system to validate trillions of training and serving examples per day"
- p. 2 (Our Contributions): "a fundamental piece of our solution is the familiar concept of a data schema, which codifies the expectations for correct data." -- adapted to hold ML-specific properties.
- p. 2 (Our Contributions): "statistical tests for detecting changes in the data distribution, such as the chi-squared test, are too sensitive and also uninformative for the typical scale of data in ML pipelines"
- pp. 2-3 (Our Contributions): "in database systems the schema comes first" whereas "in our setup the data comes first" -- so the schema is inferred from the data and co-evolves with it, with humans encoding domain knowledge.
- p. 3 (Our Contributions): "we use the schema to perform unit tests for the training algorithm." -- discrepancies mean either the schema or the training code must change.
- p. 3 (Our Contributions): "some parts of its implementation have been influenced by the specific infrastructure that we use." -- stated limit; the authors believe the design generalises and open-sourced the libraries.
- p. 3 (2 System Overview): "each batch of input data will trigger a new run of the data-validation logic" -- batches are larger time intervals (say a day), not training mini-batches.
- p. 3 (2 System Overview): "by validating over the entire batch we ensure that anomalies that are infrequent or manifest in small but important slices of data are not silently ignored." -- sampling is supported but disabled by default.
- pp. 3-4 (2 System Overview): three components: a Data Analyzer computing statistics, a Data Validator checking properties against a Schema, and a Model Unit Tester "that checks for errors in the training code using synthetic data generated through the schema."
- p. 4 (2 System Overview): "Single-batch validation answers the question: are there any anomalies in a single batch of data?"
- p. 4 (2 System Overview): "Inter-batch validation answers the question: are there any significant changes between the training and serving data, or between successive batches of the training data?"
- p. 4 (2 System Overview): "Model testing answers the question: are there any assumptions in the training code that are not reflected in the data"
- p. 4 (2 System Overview): "we acknowledge that these checks are not exhaustive, but our experience shows that they cover the vast majority of errors we have observed in production" -- stated limit.
- p. 4 (3 Single-Batch Validation): "we consider any deviation within a batch from the expected data characteristics, given expert domain knowledge, as an anomaly."
- p. 4 (3 Single-Batch Validation): "The schema acts as a logical model of the data and attempts to capture some of the semantics that are lost" -- example: age 150 is an error for a person in years but valid for a document in days.
- p. 4 (3 Single-Batch Validation): "the presence constraint covers bugs that cause the data-generation code to silently drop features from some examples" -- constraints cover type, domain, valency and code-centric error patterns.
- p. 5 (3 Single-Batch Validation): "we do not make any claims on completeness – there are reasonable data properties that our schema cannot encode." -- yet it captures "the vast majority of use cases in production pipelines."
- p. 5 (3, Schema Validation): "Any disagreement is flagged as an anomaly and triggers an alert to the on-call for further investigation."
- p. 5 (3, Schema Validation): "Our strategy of validating using these pre-computed statistics allows the validation itself to be fairly lightweight." -- which allows near-instant revalidation against an updated schema.
- p. 5 (3, Schema Validation): anomalies should "be easily interpretable and narrowly focused on the exact anomaly" -- each has a description template populated with the concrete values.
- p. 5 (3, Schema Validation): the validator includes suggested schema updates for anomalies "that correspond to the natural evolution of the data" -- e.g. a new IMPRESSIONS value for the event feature.
- p. 5 (3, Schema Validation): "avoids false positives by focusing on the narrow set of constraints that can be expressed in our schema and by requiring that the schema is manually curated"
- p. 5 (3, Schema Life Cycle): "the upfront effort in schema construction can discourage engineers from setting up data validation until they run into a serious data error." -- so a basic schema is synthesized from all available batches.
- p. 5 (3, Schema Life Cycle): "an overfitted schema is more likely to cause spurious alerts" -- which raises cognitive overhead, reduces trust and "may even lead them to switch off data validation altogether."
- p. 5 (3, Schema Life Cycle): "We currently rely on a set of reasonable heuristics to perform this initial schema inference." -- a formal solution is named future work.
- pp. 5-6 (3, Schema Life Cycle): "We expect owners of pipelines to treat the schema as a production asset at par with source code and adopt best practices for reviewing, versioning, and maintaining the schema." -- the schema is stored in the source version-control system.
- p. 6 (4 Inter-Batch Validation): "most common is different code paths used for generation of training and serving data." -- the main cause of training-serving skew.
- p. 6 (4, Feature skew): "a developer adds or removes a feature from the training-data code path but inadvertently forgets to do the same to the serving path." -- also time travel, where a non-static source is queried later for training (click counts appear higher).
- p. 6 (4, Distribution skew): "Any flaw in the sampling scheme can result in training data distributions that look significantly different from serving data distributions."
- p. 6 (4, Scoring/Serving Skew): "This establishes an implicit feedback loop which further increases the chances of misprediction for lower ranked items" -- unserved items get no labels; this skew is the hardest to detect.
- p. 6 (4 Inter-Batch Validation): "To detect feature skew, the Data Validator component does a key-join between corresponding batches of training and serving data followed by a feature wise comparison."
- p. 6 (4 Inter-Batch Validation): "the parameters for skew detection are encoded as additional constraints in the schema."
- p. 6 (4, Quantifying Distribution Distance): "in practice, we expect these distributions to be different" -- the question is whether the distance warrants an alert; KL divergence or cosine thresholds are hard for teams to interpret and tune.
- pp. 6-7 (4, Quantifying Distribution Distance): "the variance of test statistics typically has an inverse ... square relationship to the total number of examples" -- making goodness-of-fit tests sensitive to minute differences.
- p. 7 (4, Quantifying Distribution Distance): experiment: 100 million N(0,1) points with 10 thousand replaced from N(0,2), a 0.01% change; the chi-square test "would needlessly fire an alert 7 out of 10 times and would most likely be considered a flaky detection method." -- repeated with real error-free data with qualitatively the same results.
- p. 7 (4, Quantifying Distribution Distance): the chosen metric d-infinity is the largest change in probability for any value, which "makes it easier for teams to set a threshold" -- and an alert comes with a culprit value, e.g. a backend producing a default -1.
- p. 7 (4, Quantifying Distribution Distance): "We develop a method to do that based on Dirichlet priors." -- for estimating the metric soundly from observed frequencies (Appendix B).
- p. 7 (5 Model Unit Testing): "mismatches between the expected data and the assumptions made in the training code." -- the training code is a black box to the platform.
- p. 7 (5 Model Unit Testing): the logarithm example: data validation detects no errors, the model carries the hidden assumption, and a non-positive serving value causes "a (possibly crashing) failure inside the serving infrastructure."
- p. 7 (5 Model Unit Testing): "the danger of these assumptions is that they are not part of the schema" -- and they may be satisfied by the specific training data, so they do not trigger during training.
- p. 7 (5 Model Unit Testing): "We base our approach on fuzz testing (Miller et al., 1990), using the schema to guide the generation of synthetic inputs."
- p. 8 (5 Model Unit Testing): "The generation can be seeded so that it provides a deterministic output."
- p. 8 (5 Model Unit Testing): "Doing both provides for additional robustness" -- fixing the training code and extending the schema.
- p. 8 (5 Model Unit Testing): "This fuzz-testing strategy is obviously not fool-proof" -- stated limit; in practice a modest number of examples (in the 100s) triggers common errors, and the test is in the platform's standard templates.
- p. 8 (6.1 Results from Production Deployment): based on "a sample of more than 700 ML pipelines that employ data validation" -- workflow: infer schema, review and edit it, commit it to version control, then on each alert fix the data or update the schema.
- p. 8 (6.1): "The majority of cases have up to five schema revisions, with the distribution tapering off after that point." -- read as data that evolve but are not completely volatile, and as engineers treating the schema as a production asset.
- pp. 8-9 (6.1): "anecdotal evidence from some teams suggest a mental shift towards a datacentric view of ML" -- the schema also documents new features for the team.
- p. 9 (Table 1): method: Used is the fraction of pipelines whose schema could fire an alert type; Fired the fraction with an anomaly on any day; Fixed if two days without it afterwards. "This methodology can miss some fixes" -- stated limit, and fixes may be counted when a pipeline stopped.
- p. 9 (6.1): "the most common anomalies are new feature columns, unexpected string values, and missing feature columns." -- missing features and missing data are more cause for concern.
- p. 9 (6.1): "Even in cases where the anomalies almost never fire, this check is useful." -- said of the wrong-physical-type check.
- p. 9 (6.1): "product teams fix the majority of the detected anomalies." -- unfixed ones are attributed to batches sliding out of the window and to operators who "might miss or ignore the alert depending on their cognitive load."
- p. 9 (6.1): "more than 70% of pipelines had at least one model unit test defined." -- over a month the tests ran more than 80K times; 6% had failures.
- p. 9 (6.2 Case Studies): Google Play found features "always missing from the logs, but always present in training" -- removing this skew improved app install rate on the landing page by 2% in an online A/B experiment.
- pp. 9-10 (6.2 Case Studies): in a migration, a backend stored features in a different format, which "caused these features to be silently dropped in their ... data-parsing code. In this case, the hard part was identifying the features" -- diagnosis and fix took two days "whereas similar issues have taken months to resolve."
- p. 10 (6.2 Case Studies): some teams run the system for stand-alone data validation without training or serving, and two teams used it to validate a feature-store migration.
- p. 10 (7 Related Work): "we opted to have a restrictive schema definition language" -- in contrast to Amazon's arbitrary constraints, to allow effective tools for managing the schema.
- p. 10 (7 Related Work): "our approach is to avoid statistical tests that lead to false positive alerts and instead rely on more interpretable metrics of distribution distance"
- p. 13 (Appendix A): "a change in the data type from integer to string can easily cause the trainer to fail and is therefore considered a serious anomaly."
- p. 13 (Appendix A): "Our schema allows tagging of features with the stage of life cycle that they are currently in." -- because the gravity of an anomaly depends on the stage (PLANNED, ALPHA, BETA, PRODUCTION, DEPRECATED, DEBUG_ONLY).
- p. 13 (Appendix A): a domain "can also encode the semantic type of the data, which can be different than the raw type" -- e.g. TRUE/FALSE strings as booleans, integers as categorical ids.
- p. 14 (Appendix B): "for the datasets that we care about, the empirical drift d∞ (p̂, q̂) is a sound approximation of the theoretical drift." -- when counts are at least a billion and fewer than 100 values.
- p. 14 (Appendix B): "the magnitude of d1 directly corresponds to the number of examples impacted" -- d1 also corresponds to how visually distinguishable two distributions are.

## Readings for our work
- Write an explicit schema for each game-log table we load into DuckDB (column types, allowed domains such as player ids and turn ranges, presence per turn) and check every new log against it before any figure is computed; keep the schema in git next to the loader and review changes to it like code. Rests on: schema as codified expectations (p. 2), schema as production asset in version control (pp. 5-6), presence constraints for silently dropped fields (p. 4). Would not apply if: the logs are produced by a fixed, versioned DLL whose output format is itself tested.
- Our likely error source is code, not noise: a patched DLL or a changed logger can pin a field to a default (such as -1 or 0) for a slice of players or turns. Report per-column largest frequency change between a new log and a reference log, with the culprit value, rather than only aggregate outcomes. Rests on: Example 1.1 (p. 2), bugs in code as common source (p. 2), d-infinity with culprit value (p. 7). Would not apply if: aggregate win rates are the only quantity ever used.
- Do not use the A/B outcome itself as the check that the data are sound: a logging bug can leave the aggregate looking fine. Validate the harness logs separately before the Welch test. Rests on: reliance on second-order effects (p. 2). Would not apply if: the harness re-derives outcomes from the save rather than from logs.
- Keep checks few, precise and actionable; a check that fires spuriously teaches people to bypass it (which matches our history of circumvented checks). For each check record how often it fired and how often the firing led to a fix, and drop or narrow checks with spurious firings. Rests on: spammy alerts ignored (p. 2), overfitted schema leads to switching off validation (p. 5), Table 1 Used/Fired/Fixed method (p. 9). Would not apply if: a check is cheap to satisfy and never fires spuriously.
- For seeded experiments, compare distributions of harness inputs between variant and baseline runs (map, starts, opponents) to detect skew between the two arms, analogous to training-serving skew from separate code paths. Rests on: feature skew from separate code paths (p. 6). Would not apply if: both arms are generated by the same code with only the seed differing.
- When significance tests run on very large log tables (all units over all turns), expect tiny differences to be significant; state effect sizes with interpretable units next to any p-value. Rests on: chi-square sensitivity experiment (pp. 6-7). Would not apply if: the test is on 30 run-level outcomes, where the sample is small.
- Fuzz the analysis tools with seeded synthetic tables generated from the schema to expose hidden assumptions (e.g. a log on a non-positive value, a player missing on a turn). Rests on: model unit testing by schema-guided fuzzing (pp. 7-8). Would not apply if: the tools have no data-dependent transforms.
