## What it says

### Chapter 1: Getting Started

- p. 16 (About Version Control; Local Version Control Systems): "Version control is a system that records changes to a file or set of files over time so that you can recall specific versions later." A VCS lets you "see who last modified something that might be causing a problem, who introduced an issue and when" -- definition and stated uses. copying files into another directory is common, "This approach is very common because it is so simple, but it is also incredibly error prone." -- easy to write to the wrong file or copy over files.
- p. 18 (Centralized Version Control Systems; Distributed Version Control Systems): advantages are shared visibility and administration; the downside "The most obvious is the single point of failure that the centralized server represents." and "whenever you have the entire history of the project in a single place, you risk losing everything" clients "fully mirror the repository, including its full history" so "Every clone is really a full backup of all the data."
- pp. 19-20 (Distributed Version Control Systems; A Short History of Git): several remotes allow collaboration with different groups; "This allows you to set up several types of workflows that aren’t possible in centralized systems, such as hierarchical models." Git was written in 2005 after the BitKeeper licence was revoked; its goals included speed, simple design, "Strong support for non-linear development (thousands of parallel branches)", full distribution and efficiency on large projects.
- pp. 20-22 (Snapshots, Not Differences; Nearly Every Operation Is Local): other systems "store information as a list of file-based changes" (delta-based); Git takes a picture of all files at each commit, and "if files have not changed, Git doesn’t store the file again, just a link to the previous identical file it has already stored" -- "Git thinks about its data more like a stream of snapshots." "Because you have the entire history of the project right there on your local disk, most operations seem almost instantaneous." and "there is very little you can’t do if you’re offline or off VPN"
- p. 22 (Git Has Integrity; Git Generally Only Adds Data): "Everything in Git is checksummed before it is stored and is then referred to by that checksum." "You can’t lose information in transit or get file corruption without Git being able to detect it." The checksum is a 40-character SHA-1; "Git stores everything in its database not by file name but by the hash value of its contents." nearly all actions "only add data to the Git database"; uncommitted changes can be lost, but "after you commit a snapshot into Git, it is very difficult to lose, especially if you regularly push your database to another repository"
- pp. 22-23 (The Three States): "Git has three main states that your files can reside in: modified, staged, and committed"; "Staged means that you have marked a modified file in its current version to go into your next commit snapshot." "The staging area is a file, generally contained in your Git directory, that stores information about what will go into your next commit." "The Git directory is where Git stores the metadata and object database for your project." Workflow: modify, then "You selectively stage just those changes you want to be part of your next commit", then commit.
- pp. 24-27 (The Command Line; First-Time Git Setup): the book uses the command line because "the command line is the only place you can run all Git commands"; "This book was written using Git version 2." configuration lives at system, user (--global) and repository (--local, the default) level; "Each level overrides values in the previous level, so values in .git/config trump those in [path]/etc/gitconfig."
- pp. 28-29 (Your Identity; Your Editor; Your default branch name): set user.name and user.email first, because "every Git commit uses this information, and it’s immutably baked into the commits you start creating"; per project "you can run the command without the --global option when you’re in that project" without the editor set up "you get into a really confusing state when Git attempts to launch it"; "From Git version 2.28 onwards, you can set a different name for the initial branch."
- pp. 29-30 (Checking Your Settings; Getting Help): a key may be read from several files and "Git uses the last value for each unique key it sees."; with --show-origin "you can query Git as to the origin for that value, and it will tell you which configuration file had the final say in setting that value" "there are three equivalent ways to get the comprehensive manual page (manpage) help" (git help, --help, man); "These commands are nice because you can access them anywhere, even offline." The -h option gives a short option list.
### Chapter 2: Git Basics

- pp. 32-33 (Getting a Git Repository; Cloning an Existing Repository): two ways: "You can take a local directory that is currently not under version control, and turn it into a Git repository" or clone an existing one. clone, not checkout: "instead of getting just a working copy, Git receives a full copy of nearly all data that the server has"; a clone can restore a corrupted server, though "you may lose some server-side hooks and such, but all the versioned data would be there"
- pp. 34-35 (Recording Changes to the Repository; Checking the Status of Your Files): "Tracked files are files that were in the last snapshot, as well as any newly staged files"; "In short, tracked files are files that Git knows about." Untracked files are everything else. Git does not include untracked files until told to; "It does this so you don’t accidentally begin including generated binary files or other files that you did not mean to include."
- pp. 36-37 (Tracking New Files; Staging Modified Files): "the version of the file at the time you ran git add is what will be in the subsequent historical snapshot"; git add is best thought of as "add precisely this content to the next commit" rather than adding a file to the project. a file can be both staged and unstaged: "It turns out that Git stages a file exactly as it is when you run the git add command." "If you modify a file after you run git add, you have to run git add again to stage the latest version of the file"
- p. 38 (Short Status; Ignoring Files): git status -s has two columns: "the lefthand column indicates the status of the staging area and the right-hand column indicates the status of the working tree" files to ignore "These are generally automatically generated files such as log files or files produced by your build system."; "Setting up a .gitignore file for your new repository before you get going is generally a good idea so you don’t accidentally commit files that you really don’t want in your Git repository." Rules include globs, a leading slash against recursion, a trailing slash for directories, and "You can negate a pattern by starting it with an exclamation point (!)."
- pp. 39-40 (Ignoring Files; Viewing Your Staged and Unstaged Changes): nested files: "The rules in these nested .gitignore files apply only to the files under the directory where they are located." "The Linux kernel source repository has 206 .gitignore files." git status lists names; "git diff shows you the exact lines added and removed — the patch, as it were". Plain git diff "compares what is in your working directory with what is in your staging area."; git diff --staged "compares your staged changes to your last commit"; "git diff by itself doesn’t show all changes made since your last commit — only changes that are still unstaged"
- pp. 42-43 (Committing Your Changes): "anything that is still unstaged — any files you have created or modified that you haven’t run git add on since you edited them — won’t go into this commit" commit -v "puts the diff of your change in the editor so you can see exactly what changes you’re committing"; "Remember that the commit records the snapshot you set up in your staging area."
- pp. 43-44 (Skipping the Staging Area; Removing Files): "Adding the -a option to the git commit command makes Git automatically stage every file that is already tracked before doing the commit"; "This is convenient, but be careful; sometimes this flag will cause you to include unwanted changes." git rm stages a removal; -f is required for modified or staged files: "This is a safety feature to prevent accidental removal of data that hasn’t yet been recorded in a snapshot and that can’t be recovered from Git." With --cached "you may want to keep the file on your hard drive but not have Git track it anymore", e.g. a log file staged by mistake.
- pp. 45-46 (Moving Files; Viewing the Commit History): "Git doesn’t explicitly track file movement" -- "If you rename a file in Git, no metadata is stored in Git that tells it you renamed the file." git mv equals mv, rm, add; "Git figures out that it’s a rename implicitly" git log "lists the commits made in that repository in reverse chronological order" with hash, author, date and message.
- pp. 47-48 (Viewing the Commit History): -p shows each commit's patch; "This is very helpful for code review or to quickly browse what happened during a series of commits that a collaborator has added." --stat gives per-file counts. --pretty=format "is especially useful when you’re generating output for machine parsing — because you specify the format explicitly, you know it won’t change with updates to Git"
- pp. 49-51 (Viewing the Commit History; Limiting Log Output): "The author is the person who originally wrote the work, whereas the committer is the person who last applied the work." --graph adds an ASCII branch and merge graph. -n, "the time-limiting options such as --since and --until are very useful", --author, --grep; the pickaxe -S "takes a string and shows only those commits that changed the number of occurrences of that string"; a path argument limits output "to commits that introduced a change to those files"
- p. 52 (Limiting Log Output; Undoing Things): a combined filter example: "Of the nearly 40,000 commits in the Git source code history, this command shows the 6 that match those criteria." --no-merges hides merge commits, which "typically aren’t very informative" "This is one of the few areas in Git where you may lose some work if you do it wrong." commit --amend reuses the staging area and "it overwrites your previous commit"
- pp. 53-54 (Undoing Things; Unstaging a Staged File): amending means "you’re not so much fixing it as replacing it entirely with a new, improved commit"; "Only amend commits that are still local and have not been pushed somewhere." "Amending previously pushed commits and force pushing the branch will cause problems for your collaborators." git status itself names the undo command (git reset HEAD <file>); "It’s true that git reset can be a dangerous command, especially if you provide the --hard flag." In the unstage case the working file is not touched.
- pp. 54-56 (Unmodifying a Modified File; Undoing things with git restore): "It’s important to understand that git checkout -- <file> is a dangerous command." "Any local changes you made to that file are gone"; stashing and branching are better ways to set work aside. "Remember, anything that is committed in Git can almost always be recovered." "However, anything you lose that was never committed is likely never to be seen again." "Git version 2.23.0 introduced a new command: git restore." restore --staged unstages; "git restore <file> is a dangerous command" for the same reason.
- pp. 56-58 (Working with Remotes; Showing Your Remotes; Adding Remote Repositories): "Remote repositories are versions of your project that are hosted on the Internet or network somewhere." "each of which generally is either read-only or read/write for you"; the word remote "does not necessarily imply that the repository is somewhere else on the network or Internet, only that it is" elsewhere origin is "that is the default name Git gives to the server you cloned from"; git remote add <shortname> <url> adds others, whose branches then appear as e.g. pb/master.
- p. 59 (Fetching and Pulling from Your Remotes; Pushing to Your Remotes): "the git fetch command only downloads the data to your local repository — it doesn’t automatically merge it with any of your work or modify what you’re currently working on"; "Running git pull generally fetches data from the server you originally cloned from and automatically tries to merge it into the code you’re currently working on." From 2.27, git pull warns until pull.rebase is set. "If you and someone else clone at the same time and they push upstream and then you push upstream, your push will rightly be rejected." "You’ll have to fetch their work first and incorporate it into yours before you’ll be allowed to push."
- pp. 60-62 (Inspecting a Remote; Renaming and Removing Remotes; Tagging; Creating Tags): git remote show "also shows you which remote branches on the server you don’t yet have, which remote branches you have that have been removed from the server"; after removal "all remote-tracking branches and configuration settings associated with that remote are also deleted" "Typically, people use this functionality to mark release points (v1.0, v2.0 and so on)." "A lightweight tag is very much like a branch that doesn’t change — it’s just a pointer to a specific commit." "Annotated tags, however, are stored as full objects in the Git database." with tagger, date, message and optional GPG signature; "It’s generally recommended that you create annotated tags so you can have all this information"
- pp. 63-65 (Tagging Later; Sharing Tags; Deleting Tags): "You can also tag commits after you’ve moved past them." -- "you specify the commit checksum (or part of it) at the end of the command" "By default, the git push command doesn’t transfer tags to remote servers."; --tags pushes all, with "--follow-tags only annotated tags will be pushed to the remote"; git tag -d "Note that this does not remove the tag from any remote servers."
- pp. 66-68 (Checking out Tags; Git Aliases): checking out a tag gives detached HEAD; a commit made there "your new commit won’t belong to any branch and will be unreachable, except by the exact commit hash", so create a branch to fix an old version. aliases are set with git config; "For clarity’s sake, we won’t be using them anywhere else in this book"; "This technique can also be very useful in creating commands that you think should exist." A leading ! runs an external command: "This is useful if you write your own tools that work with a Git repository."
### Chapter 3: Git Branching

- p. 69 (Git Branching; Branches in a Nutshell): "Branching means you diverge from the main line of development and continue to do work without messing with that main line." "Git encourages workflows that branch and merge often, even multiple times in a day." a commit object holds a pointer to the staged snapshot, author, message and "pointers to the commit or commits that directly came before this commit (its parent or parents)"; after the first commit "Your Git repository now contains five objects" (three blobs, one tree, one commit).
- pp. 70-72 (Branches in a Nutshell; Creating a New Branch): "A branch in Git is simply a lightweight movable pointer to one of these commits." The master "branch in Git is not a special branch"; it exists only because git init creates it. git branch creates a pointer but does not switch; HEAD: "In Git, this is a pointer to the local branch you’re currently on."
- pp. 74-75 (Switching Branches): "by default, git log will only show commit history below the branch you’ve checked out" -- "To show all of the branches, add --all to your git log command." Switching rewrites the working directory; "If Git cannot do it cleanly, it will not let you switch at all." a branch is a file holding a SHA-1, so "Creating a new branch is as quick and simple as writing 41 bytes to a file (40 characters and a newline)."; because parents are recorded, "finding a proper merge base for merging is automatically done for us"
- pp. 76-78 (Switching Branches; Basic Branching and Merging; Basic Branching): "From Git version 2.23 onwards you can use git switch instead of git checkout". The example workflow: a branch per user story; for an urgent fix, switch to production, branch, "After it’s tested, merge the hotfix branch, and push to production." "With Git, you don’t have to deploy your fix along with the iss53 changes you’ve made"; "It’s best to have a clean working state when you switch branches."
- pp. 79-82 (Basic Branching; Basic Merging): "You can run your tests, make sure the hotfix is what you want, and finally merge the hotfix branch back into your master branch to deploy to production." A fast-forward: "Git simplifies things by moving the pointer forward because there is no divergent work to merge together" with diverged history "Git does a simple three-way merge, using the two snapshots pointed to by the branch tips and the common ancestor of the two"; "This is referred to as a merge commit, and is special in that it has more than one parent."
- pp. 82-86 (Basic Merge Conflicts; Branch Management): "If you changed the same part of the same file differently in the two branches you’re merging, Git won’t be able to merge them cleanly." "It has paused the process while you resolve the conflict."; you edit the marked sections, and "Staging the file marks it as resolved in Git." In the merge message "you can modify this commit message with details about how you resolved the merge and explain why you did the changes you made if these are not obvious" with git branch --merged, "Branches on this list without the * in front of them are generally fine to delete with git branch -d"; unmerged branches refuse -d; "If you really do want to delete the branch and lose that work, you can force it with -D"
- pp. 86-89 (Changing a branch name; Long-Running Branches): "Do not rename branches that are still in use by other collaborators." Renaming master "will break the integrations, services, helper utilities and build/release scripts that your repository uses"; "make sure you do a thorough search through your repo and update any references to the old branch name in your code and scripts". Tasks include "Update any test-runner configuration files." and "Adjust build and release scripts." "merging from one branch into another multiple times over a long period is generally easy to do"; many keep "only code that is entirely stable in their master branch — possibly only code that has been or will be released" and a develop or next branch; "sets of commits graduate to a more stable silo when they’re fully tested"; "having multiple long-running branches isn’t necessary, but it’s often helpful, especially when you’re dealing with very large or complex projects"
- pp. 89-91 (Topic Branches): "A topic branch is a short-lived branch that you create and use for a single particular feature or related work." "because your work is separated into silos where all the changes in that branch have to do with that topic, it’s easier to see what has happened during code review and such"; you "merge them in when they’re ready, regardless of the order in which they were created or worked on"; abandoned topics (iss91) are thrown away. "these branches are completely local" -- no communication with the server while branching and merging.
- pp. 92-97 (Remote Branches; Pushing): remote-tracking branches: "They’re local references that you can’t move; Git moves them for you whenever you do any network communication"; "Think of them as bookmarks, to remind you where the branches in your remote repositories were the last time you connected to them." "as long as you stay out of contact with your origin server, your origin/master pointer doesn’t move" "Your local branches aren’t automatically synchronized to the remotes you write to — you have to explicitly push the branches you want to share." "you can use private branches for work you don’t want to share"
- pp. 98-99 (Pushing; Tracking Branches): "when you do a fetch that brings down new remote-tracking branches, you don’t automatically have local, editable copies of them"; you merge them or base a local branch on them. "Tracking branches are local branches that have a direct relationship to a remote branch." git pull on them knows what to fetch and merge; -u / --set-upstream-to sets the upstream.
- pp. 100-101 (Tracking Branches; Pulling; Deleting Remote Branches): git branch -vv shows ahead/behind, but "It’s important to note that these numbers are only since the last time you fetched from each server." "This command does not reach out to the servers, it’s telling you about what it has cached from these servers locally." git pull is "essentially a git fetch immediately followed by a git merge in most cases" git push --delete: "Basically all this does is to remove the pointer from the server." "The Git server will generally keep the data there for a while until a garbage collection runs"
- pp. 101-103 (Rebasing; The Basic Rebase): "there are two main ways to integrate changes from one branch into another: the merge and the rebase"; "With the rebase command, you can take all the changes that were committed on one branch and replay them on a different branch." It goes to the common ancestor, saves each commit's diff, resets to the target, and applies each in turn. "There is no difference in the end product of the integration, but rebasing makes for a cleaner history." "it appears that all the work happened in series, even when it originally happened in parallel"; used to submit to a project you do not maintain: "That way, the maintainer doesn’t have to do any integration work — just a fast-forward or a clean apply." The final snapshot is the same, "it’s only the history that is different"
- pp. 103-106 (More Interesting Rebases; The Perils of Rebasing): git rebase --onto master server client means "Take the client branch, figure out the patches since it diverged from the server branch" and replay them on master, to release client changes while server changes are tested further. "Do not rebase commits that exist outside your repository and that people may have based work on." "When you rebase stuff, you’re abandoning existing commits and creating new ones that are similar but different."; if others based work on them, "your collaborators will have to re-merge their work and things will get messy"
- pp. 107-109 (The Perils of Rebasing; Rebase When You Rebase): after a force push and a pull you get duplicate commits: "you’ll see two commits that have the same author, date, and message, which will be confusing" "Git also calculates a checksum that is based just on the patch introduced with the commit" (patch-id), so rebasing onto the rewritten branch can drop duplicates; "This only works if C4 and C4' that your partner made are almost exactly the same patch."; after a forced rewrite "make sure everyone knows to run git pull --rebase"
- pp. 109-110 (Rebase When You Rebase; Rebase vs. Merge): rebasing only never-pushed commits is fine; "If you rebase commits that have been pushed, but that no one else has based commits from, you’ll also be fine." one view: "your repository’s commit history is a record of what actually happened" -- "It’s a historical document, valuable in its own right, and shouldn’t be tampered with."; the other: "the commit history is the story of how your project was made" told for future readers. "every team and every project is different"; "rebase local changes before pushing to clean up your work, but never rebase anything that you’ve pushed somewhere"
### Chapter 5: Distributed Git

- pp. 132-133 (Distributed Workflows; Centralized Workflow): in Git "every developer is potentially both a node and a hub"; of the workflows shown "you can choose a single one to use, or you can mix and match features from each" "The second developer must merge in the ... first one’s work before pushing changes up, so as not to overwrite the first developer’s changes." "Git won’t let users overwrite each other."; "it’s possible for hundreds of developers to successfully work on a single project through dozens of branches simultaneously"
- pp. 133-135 (Integration-Manager Workflow; Dictator and Lieutenants Workflow; Patterns for Managing Source Code Branches): "each developer has write access to their own public repository and read access to everyone else’s"; steps end with "The maintainer adds the contributor’s repository as a remote and merges locally." and pushes to the main repository; common with GitHub or GitLab forks; "Contributors don’t have to wait for the project to incorporate their changes — each party can work at their own pace." "Various integration managers are in charge of certain parts of the repository; they’re called lieutenants." "This kind of workflow isn’t common, but can be useful in very big projects, or in highly hierarchical environments." It lets the leader "delegate much of the work and collect large subsets of code at multiple points before integrating them". Fowler's guide is cited: "There’s also a section comparing high and low integration frequencies."
- pp. 135-136 (Contributing to a Project; Commit Guidelines): "Some of the variables involved are active contributor count, chosen workflow, your commit access, and possibly the external contribution method." "Changes you submit may be rendered obsolete or severely broken by work that is merged in while you were working or while your changes were waiting to be approved or applied." "The workflow required in order to contribute to a project is much different if you have write access to the project than if you don’t." based on the Git project's SubmittingPatches: "your submissions should not contain any whitespace errors"; before committing "run git diff --check, which identifies possible whitespace errors and lists them for you"
- p. 136 (Commit Guidelines): "try to make each commit a logically separate changeset"; "don’t code for a whole weekend on five different issues and then submit them all as one massive commit on Monday" but "use the staging area on Monday to split your work into at least one commit per issue, with a useful message per commit"; "If some of the changes modify the same file, try to use git add --patch to partially stage files" "The project snapshot at the tip of the branch is identical whether you do one commit or five"; "This approach also makes it easier to pull out or revert one of the changesets if you need to later." Use history-rewriting tools to "craft a clean and understandable history before sending the work to someone else"
- pp. 136-137 (Commit Guidelines): "As a general rule, your ... messages should start with a single line that’s no more than about 50 characters and that describes the changeset concisely, followed by a blank line, followed by a more detailed explanation"; "The Git project requires that the more detailed explanation include your motivation for the change and contrast its implementation with previous behavior"; "Write your commit message in the imperative" the Tim Pope template: "Wrap it to about 72 characters or so." "The blank line separating the summary from the body is critical (unless you omit the body entirely)"; the imperative "matches up with commit messages generated by commands like git merge and git revert"; the authors admit "many of the examples in this book don’t have nicely-formatted commit messages like this" -- "In short, do as we say, not as we do."
- pp. 137-139 (Private Small Team): with shared push access the workflow resembles Subversion, but "the main difference is that merges happen client-side rather than on the server at commit time" John's push is rejected although the files differ: "Although Subversion automatically does such a merge on the server if different files are edited, with Git, you must first merge the commits locally."
- pp. 140-142 (Private Small Team): after merging, "John might want to test this new code to make sure none of Jessica’s work affects any of his" before pushing. "The issue54..origin/master syntax is a log filter that asks Git to display only those commits that are on the latter branch" and not on the first; merge order: "The end snapshot should be identical no matter which order she chooses; only the history will be different."
- pp. 143-149 (Private Small Team; Private Managed Team): the general pattern: "You work for a while (generally in a topic branch), and merge that work into your master branch when it’s ready to be integrated." then fetch, merge origin/master, push. "the work of the individual groups is integrated only by certain engineers, and the master branch of the main repo can be updated only by those engineers"; developers share feature branches (push -u, refspec featureB:featureBee); "The ability of smaller subgroups of a team to collaborate via remote branches without necessarily having to involve or impede the entire team is a huge benefit of Git."
- pp. 150-151 (Forked Public Project): "You may want to use rebase -i to squash your work down to a single commit, or rearrange the work in the commits to make the patch easier for the maintainer to review"; "It’s easiest to push the topic branch you’re working on to your forked repository, rather than merging that work into your master branch and pushing that." because "if your work isn’t accepted or is cherry-picked, you don’t have to rewind your master branch" the maintainer is notified by "This is often called a pull request" or by git request-pull, whose output "tells them where the work was branched from, summarizes the commits, and identifies from where the new work is to be pulled"
- pp. 151-152 (Forked Public Project): "it’s generally easier to have a branch like master always track origin/master and to do your work in topic branches that you can easily discard if they’re rejected"; for a second topic "don’t continue working on the topic branch you just pushed up — start over from the main repository’s master branch"; each topic is "contained within a silo — similar to a patch queue — that you can rewrite, rebase, and modify without the topics interfering or interdepending on each other" if a branch no longer merges cleanly, "you can try to rebase that branch on top of origin/master, resolve the conflicts for the maintainer, and then resubmit your changes"; this needs push -f; "An alternative would be to push this new work to a different branch on the server (perhaps called featureAv2)."
- pp. 153-154 (Forked Public Project; Public Project over Email): merge --squash "squashes it into one changeset producing the repository state as if a real merge happened, without actually making a merge commit" "Many projects have established procedures for accepting patches — you’ll need to check the specific rules for each project, because they will differ." git format-patch "it turns each commit into an ... email message with the first line of the commit message as the subject"; "applying a patch from an email generated with format-patch preserves all the commit information properly"
- pp. 154-156 (Public Project over Email; Maintaining a Project): text between the --- line and the diff is read by developers but "content is ignored by the patching process"; "Pasting the text often causes formatting issues, especially with" ... "clients that don’t preserve newlines and other whitespace appropriately"; git imap-send and git send-email (pp. 155-156) send patches unmangled. "you need to know how to accept work in a way that is clearest for other contributors and sustainable by you over the long run"
- p. 157 (Working in Topic Branches; Applying a Patch with apply): try new work "in a topic branch — a temporary branch specifically made to try out that new work"; "The maintainer of the Git project tends to namespace these branches as well" (sc/ruby_client). git apply "it’s more paranoid and accepts fewer fuzzy matches than patch", handles adds, deletes and renames, and is an all-or-nothing "model where either everything is applied or nothing is, whereas patch can partially apply patchfiles, leaving your working directory in a weird state"; "It won’t create a commit for you"
- p. 158 (Applying a Patch with apply; Applying a Patch with am): git apply --check: "If there is no output, then the patch should apply cleanly." "This command also exits with a non-zero status if the check fails, so you can use it in scripts if you want." "If you can, encourage your contributors to use format-patch instead of diff to generate patches for you." "You should only have to use git apply for legacy patches and things like that." git am creates the commit; "The author information is taken from the email’s From and Date headers"
- pp. 159-160 (Applying a Patch with am): "The Commit information indicates the person who applied the patch and the time it was applied."; a patch may fail when "Perhaps your main branch has diverged too far from the branch the patch was built from, or the patch depends on another patch you haven’t applied yet."; -3 tries a three-way merge, but "This option isn’t on by default because it doesn’t work if the commit the patch says it was based on isn’t in your repository." interactive git am -i "stops at each patch it finds and asks if you want to apply it"
- pp. 160-161 (Checking Out Remote Branches; Determining What Is Introduced): adding a contributor's repository as a remote "This is most useful if you’re working with a person consistently."; "You’re also unlikely to want to have hundreds of remotes, each for someone who contributes only a patch or two." "The other advantage of this approach is that you get the history of the commits as well." -- "a proper three-way merge is the default rather than having to supply a -3 and hope the patch was generated off a public commit to which you have access" "It’s often helpful to get a review of all the commits that are in this branch but that aren’t in your master branch." ## Readings for our work
(Inferences, not claims of the source.)
- One concern per commit, split at staging time: when a session has touched code, tools and documents, stage them with git add --patch into separate commits, each with its own Serves:/Method: line, and never use commit -a on a mixed working tree. Check: before each commit, git diff --staged --stat lists only files of one concern. Rests on: p. 136 (logically separate changeset, one commit per issue, add --patch, easier to revert), pp. 43-44 (-a includes unwanted changes), p. 37 (exact staged content). Would not apply if: two changes cannot be separated without leaving a commit that fails the gate; then they are one changeset and the message says so.
- Line-ending and whitespace rewrites in DLL patches: run git diff --check on every staged patch, and git apply --check of the delivered patch against a fresh checkout of the GitLab upstream, before delivery; compare the diffstat line counts with the lines meant to change. Rests on: p. 136 (whitespace errors, diff --check), p. 158 (apply --check, non-zero exit usable in scripts), p. 157 (apply is all-or-nothing). Would not apply if: the CRLF change is introduced by a conversion that diff --check does not report; then the diffstat comparison, not diff --check, is the check.
- Deliver patches as files or branches, never as pasted text: generate them with git format-patch (or push a topic branch for a merge request) so that author, message and bytes survive; the recipient applies with git am. Rests on: pp. 153-154 (format-patch keeps commit information; pasting breaks newlines and whitespace), p. 158 (prefer format-patch over diff), p. 159 (Author vs Commit). Would not apply if: the GitLab project's rules for contributions ask for something else (p. 153: check each project's rules).
- One topic branch per merge request to the RoM repository, cut from a freshly fetched upstream master; a revised version goes to a new branch (featureAv2) or is rebased only while nobody has based work on it. Check: git log upstream/master..topic lists only the commits of that one change. Rests on: pp. 150-152 (topic branch per contribution, start over from master, rebase and resubmit, featureAv2), p. 106 and p. 109 (when rebasing is safe), p. 141 (the .. filter). Would not apply if: the upstream maintainer asks for squashed single-commit merge requests (p. 150, p. 153), which changes the shape but not the one-topic rule.
- Review what a change introduces with the three-dot diff, not a plain diff against master: git diff master...topic before merging or delivering, so that later upstream work does not show up as reverted. Rests on: p. 162 (plain diff misleading; triple-dot shows only the topic's work). Would not apply if: master is a direct ancestor of the topic (p. 162), where both diffs agree.
- Never rewrite published history in this repository: amend and rebase only commits that are not yet pushed, no force push to shared branches; the register's append-only rule fits this. Check: a pre-push hook or server rule rejects non-fast-forward pushes to master. Rests on: p. 53 (only amend local commits), p. 106 (do not rebase commits others may have based work on), p. 110 (rebase locally, never what was pushed), p. 133 (Git won't let users overwrite each other). Would not apply if: a branch is pushed only as a backup and nobody has based work on it (p. 109).
- Local hooks are not a gate others are bound by: a clone does not carry hooks (server-side hooks can be lost even when restoring from a clone), so the pre-commit and commit-msg checks only bind a clone where setup.sh has run, and can be skipped there. Rerun method/check_all.py where it cannot be bypassed (CI or the integrator before merging), not only in the hook. Rests on: p. 33 (hooks not part of the versioned data), pp. 145-149 and p. 133 (master updated only by integrators; maintainer merges after testing). Would not apply if: the repository already runs the same checks on the server side for every push to master.
- Separate the hand that checks from the hand that is checked: changes to the checks (Method: commits) go in their own commits and branches, merged only after someone other than their author, or a fixed earlier version of the checks, has run them. Rests on: pp. 133-134 (integration manager tests contributions locally before merging), pp. 145-149 (integration only by certain engineers), p. 166 (structured workflow to vet contributions). Would not apply if: there is only one contributor and no fixed reference version; then the separation is only between commits, and the readings say so.
- Generated files stay generated: rendered documents, DuckDB files, logs and build outputs are either ignored in .gitignore or, when they must be committed, regenerated by the check and compared with the committed copy, so a hand edit shows up as a difference. Rests on: p. 38 (ignore automatically generated files, set up .gitignore early), p. 35 (untracked so generated binaries are not committed by accident), p. 44 (rm --cached for files staged by mistake). Would not apply if: the rendered Markdown must be committed for reading on GitHub; then only the regenerate-and-compare check applies.
- Claims about the history from the history, not from memory: when a document says when or why something changed, cite the commit found with git log -S, --grep or git log -- path, and read status of the upstream only after git fetch. Rests on: pp. 50-51 (pickaxe, --grep, path filters), p. 100 (ahead/behind numbers are cached until the next fetch), p. 59 (fetch does not merge). Would not apply if: the claim is about uncommitted work, which the history does not hold (p. 55).
- Name every DLL build and experiment baseline by an annotated tag and git describe output, so a result can be tied to the exact code and the best existing version re-created for the Welch comparison; push tags explicitly. Rests on: p. 62 (annotated tags recommended), pp. 168-169 (tag to re-create a release; describe = tag, count, hash; describe needs annotated tags; abbreviated hash may stop being unique), p. 64 (push does not send tags). Would not apply if: builds are made from a working tree with uncommitted changes; then describe names a commit that is not what was built, and the build must first be committed.
- Commit messages in the Git project's form: a summary of at most about 50 characters in the imperative, a blank line, then a body with the motivation and the contrast with previous behaviour, with the Serves:/Method: trailers in the body. Check: the commit-msg hook can test the first line's length and the blank line. Rests on: pp. 136-137 (50 characters, blank line, motivation and contrast, imperative, 72-column wrap). Would not apply if: the GitLab upstream has its own message rules (p. 153), which then govern patches sent there.
- Long-running stability levels for this repository only if needed: a master that holds only commits that pass every check, with work done in short topic branches merged when they pass, before considering a develop or next branch. Rests on: pp. 88-90 (long-running branches not necessary, topic branches useful in projects of any size), pp. 162-164 (simple merge workflow vs two-phase for more stable projects). Would not apply if: several sessions work in parallel on overlapping files, where an integration branch that is tested before master (p. 164) is the safer form.
