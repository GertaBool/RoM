# Greg Wilson, Jennifer Bryan, Karen Cranston, Justin Kitzes, Lex Nederbragt, Tracy K. Teal, Good enough practices in scientific computing (PLoS Computational Biology 13(6): e1005510, 2017)
Source: lit3/wilson-goodenough/doc.txt. Read: lines 1-998 (all, including boxes and references).

## What it says
- p. 1 (Author summary): "most researchers are never taught the equivalent of basic lab skills for research computing." -- so data get lost and analyses take longer; practices are drawn from published sources, daily work and workshops delivered "to over 11,000 people since 2010."
- p. 1 (Overview): "Our recommendations are aimed specifically at people who are new to research computing."
- p. 2 (Introduction): "a minimum set of tools and techniques that we believe every researcher can and should consider adopting." -- the good-enough practices, as distinct from the 2014 Best Practices paper for people already doing significant computation.
- p. 2 (Introduction): the audience is "researchers who are working alone or with a handful of collaborators on projects lasting a few days to several months."
- p. 2 (Introduction): inclusion criterion: "A practice is included in our list if large numbers of researchers use it and large numbers of people are still using it months after first trying it out." -- because "there is no point in recommending something that people won’t actually adopt."
- p. 2 (Introduction): "Change is hard, and if researchers don’t see those benefits quickly enough to justify the pain, they will almost certainly switch back to their old way of doing things." -- this rules out practices like code review that they consider essential for larger-scale development.
- p. 2 (Data management): "work towards ready-to-analyze data incrementally, documenting both the intermediate data and the process."
- p. 2 (1a): "It is tempting to overwrite raw data files with cleaned-up versions, but faithful retention is essential for rerunning analyses from start to finish" -- make raw files read-only so it is harder "to hand edit it in a moment of weakness."
- p. 2 (1a): for large, stable databases "record the exact procedure used to obtain the raw data" -- with an official version number or date of download.
- p. 4 (1b): "Ensure that raw data are backed up in more than one location" -- off-site drives, institutional storage or cloud services.
- p. 4 (1c): "Create the data set you wish you had received." -- improve machine and human readability "but not to do vigorous data filtering or add external information"; use open formats, self-explaining variable names, and NA instead of artificial codes such as -99.
- p. 5 (1c): "Store especially useful metadata as part of the file name itself, while keeping the file name regular enough for easy pattern matching."
- p. 5 (1d): tidy data: "Make each column a variable" and "Make each row an observation" -- store units in their own variable or in metadata, e.g. 3.4 instead of 3.4kg.
- p. 5 (1e): "If you do not document this step thoroughly, it is impossible for you or anyone else to repeat the analysis." -- data manipulation is as integral to analysis as statistical modeling.
- p. 5 (1e): "The best way to do this is to write scripts for every stage of data processing." -- when not feasible, "clearly document every manual action" with at least what was done if not why.
- pp. 5-6 (1f): "Anticipate the need to use multiple tables, and use a unique identifier for every record" -- IDs in a common format in all tables; "give each record or unit a unique, persistent key".
- p. 6 (1g): "Your data are as much a product of your research as the papers you write" -- submit to a DOI-issuing repository; metadata for the data set as a whole and for its content.
- p. 6 (Data management): "we recommend the explicit creation and retention of intermediate products." -- saving intermediate files makes it easy to rerun parts of a pipeline; a monolithic in-memory procedure may suit projects with very little cleaning.
- p. 6 (Software): "being readable, reusable, and testable are all side effects of writing modular code" -- short, single-purpose functions with clearly defined inputs and outputs.
- p. 6 (2a): "Place a brief explanatory comment at the start of every program" -- including at least one example of use and reasonable parameter values.
- p. 7 (2b): "Decompose programs into functions (2b) that are no more than 1 page (about 60 lines) long." -- with no more than 5 or 6 input parameters and no reference to outside information; short-term memory holds about 7 items.
- p. 7 (2c): "Be ruthless about eliminating duplication" -- reuse functions and data structures instead of copying code or creating score1, score2, score3.
- p. 7 (2d, 2e): "always search for well-maintained software libraries that do what you need" -- but "test libraries before relying on them".
- p. 7 (2f): "the greater the scope of a variable, the more informative its name should be"
- pp. 7-8 (2g): "Make dependencies and requirements explicit" -- per project, e.g. a requirements.txt or a Getting Started section in the README.
- p. 8 (2h): "Do not comment and uncomment sections of code to control a program’s behavior" -- "since this is error prone and makes it difficult or impossible to automate analyses"; use if/else instead.
- p. 8 (2i): "Provide a simple example or test data set" -- to check a known correct output for a simple known input; such a smoke test is "particularly helpful when supposedly innocent changes are being made to the program".
- p. 8 (2j): "Your software is as much a product of your research as your papers" -- submit code to a DOI-issuing repository on submission.
- p. 8 (Collaboration): make it easy "for people to set up a local workspace so that they can contribute, help them find tasks" -- new collaborators may be "you returning to a project that has been idle for some time."
- p. 8 (3a): a README with title, description, contact and "an example or 2 of how to run various cleaning or analysis tasks" -- plus a CONTRIBUTING file listing dependencies, tests and guidelines.
- p. 8 (3b, 3c): a shared to-do list described "clearly so that they make sense to newcomers" and explicit decisions about communication channels.
- p. 9 (3d): "Lack of an explicit license does not mean there isn’t one; rather, it implies the author is keeping all rights" -- they recommend CC-0 or CC-BY for data and text, a permissive license for software, and against non-commercial variants and the GPL.
- p. 9 (3e): "Make the project citable (3e) by including a CITATION file in the project’s home directory"
- p. 9 (4a): "divide work into projects based on the overlap in data and code files." -- shared tools used by several projects should probably be a project of their own.
- p. 9 (Project organization): "it is useful to organize the project by the types of files and that consistency helps you effectively find and use things later."
- p. 10 (4b, 4c): text documents in doc; "raw data and metadata in a data directory and files generated during cleanup and analysis in a results directory" -- generated files include intermediate and final results.
- p. 10 (4d): src holds core analysis files and "controller or driver scripts that contain all the analysis steps for the entire project from start to finish" -- e.g. a script named runall.
- p. 11 (External scripts): "The answer is that it doesn’t matter, as long as each team’s projects follow the same rule." -- consistency and predictability over hairsplitting.
- p. 11 (4f): "Name all files to reflect their content or function" -- not sequential numbers or figure positions, "since those numbers will almost certainly change as the project evolves."
- p. 12 (Keeping track of changes): "Being able to reference or retrieve a specific version of the entire project aids in reproducibility"
- p. 12 (5a): "Back up (almost) everything created by a human being as soon as it is created" -- scripts, dependent packages and documentation.
- p. 12 (5b): "Each change should not be so large as to make the change tracking irrelevant." -- a single change adding or changing several hundred lines is likely too large; "a good size for a single change is a group of edits that you could imagine wanting to undo in one step"
- p. 12 (5c): "the effort required to merge differences goes up faster than the size of the difference." -- so share changes frequently and do not let versions drift apart.
- p. 12 (5d): "Create, maintain, and use a checklist for saving and sharing changes to the project" -- including clear log messages, size and content of changes, and "bans on committing half-done work or broken code."
- pp. 12-13 (5e): store each project in a folder mirrored off the working machine and "Synchronize that folder at least daily."
- p. 13 (5f, 5g): manual versioning: a CHANGELOG.txt with dated notes, most recent first, and a dated copy of the whole project "whenever a significant change has been made" -- one that "materially affects the results".
- p. 13 (Data are cheap, time is expensive): "a terabyte hard drive costs about US$50 retail" -- so whole copies cost less than the time to select files by hand.
- p. 14 (Version control systems): "What the manual process described above requires most is self-discipline." -- version control tools "automate some steps while enforcing others and thereby require less self-discipline for more reliable results."
- p. 14 (Box 4): version control keeps "a 100% accurate record of what was actually changed as opposed to what the user thought they changed" -- and prompts for a log message on every saved change.
- p. 15 (What not to put under version control): "changing the order of the rows or columns will create a big change for the version control system, even if the actual data have not changed."
- p. 15 (What not to put under version control): "Keeping intermediate data files and other results under version control is also not necessary if you can regenerate them from raw data and software." -- but small data and results are worth versioning for access and comparison; large files should not be included (GitHub limit 100 MB).
- p. 15 (Inadvertent sharing): "be sure not to unintentionally place security credentials such as passwords and private keys in a version control system"
- pp. 15-16 (Manuscripts): goals include "a single master document that is available to all coauthors at all times" and to "Make it easy to regenerate the final published form (e.g., a PDF) and to tell if it is up to date."
- p. 16 (The first rule is...): "The workflow you choose is less important than having all authors agree on the workflow before writing starts."
- p. 16 (6b): "Write the manuscript in a plain text format that permits version control" -- e.g. LaTeX or Markdown converted with Pandoc; this requires contributors to know a much larger set of tools.
- pp. 16-17 (Why two recommendations for manuscripts?): "We initially recommended that researchers should always use plain text in version control to manage manuscripts." -- they changed it because community members found the learning curve a significant barrier; quotes from Stephen Turner and Arjun Raj.
- p. 17 (Supplementary materials): "do not rely solely on the PDF format, since extracting data from PDFs is notoriously hard." -- put reusable results in separate text-format files.
- p. 17 (What we left out): "We have deliberately left many good tools and practices off our list" -- because they only make sense on top of the core practices or need a larger investment before paying off.
- pp. 17-18 (What we left out, Branches): branches "add an extra layer of complexity to version control for newcomers" -- they can be adopted after mastering a basic edit-commit workflow.
- p. 18 (What we left out, Build tools): "newcomers can achieve the same behavior by writing shell scripts that rerun everything"
- p. 18 (What we left out, Unit tests): "While unit tests are essential to the health of large libraries and programs, we have found that they usually aren’t compelling for solo exploratory work" -- left off as unlikely to be adopted; coverage likewise "only starts to pay off as projects grow larger".
- p. 18 (What we left out, Continuous integration): tests can run "before changes are saved (in which case, the changes can be rejected if something fails)" -- CI is "invaluable in large projects with many contributors but pay fewer dividends in smaller projects".
- p. 18 (What we left out, Profiling; Documentation): profiling only "when the program’s performance is actually a bottleneck"; "people won’t write comprehensive documentation until they have collaborators who will use it."
- p. 18 (What we left out, Code reviews and pair programming): "These practices are valuable in projects with multiple people making large software contributions, which is not typical for the intended audience"
- p. 19 (What we left out): experienced programmers do these things even for small projects because they have paid the learning cost and expect growth, but "advocating unit testing with coverage checking and continuous integration is more likely to overwhelm newcomers rather than aid them."
- p. 19 (Conclusion): "these practices make researchers more productive individually by enabling them to get more done in less time and with less pain."
- p. 19 (Conclusion): "However, progress will not happen by itself." -- the time and skills required are not valued; PIs, universities, librarians and funders should support and train.
- p. 19 (Conclusion): "it is unfair as well as counterproductive to insist that researchers do things without teaching them how."

## Readings for our work
- Treat game saves and raw logs as read-only raw data: store them once, mark them read-only, never overwrite them with cleaned versions, and record how each was obtained (scenario, build, date). Rests on: 1a save the raw data and record the procedure (p. 2). Would not apply if: a save is itself an output we regenerate from a seed, in which case record the seed and build instead.
- Generated documents and tables belong to results and are produced by a runall-style controller; editing them by hand breaks the chain from raw data to text. A check can compare the committed render with a fresh render. Rests on: 1e scripts for every stage (p. 5), 4c and 4d results directory and controller script (p. 10), regenerate and tell if up to date (pp. 15-16). Would not apply if: a document is hand-written prose with no generated content.
- Size commits as one undoable unit: one concern each, and never a mass line-ending or formatting change mixed with content. A pre-commit check can reject commits whose diff is dominated by whitespace or CRLF changes alongside other edits. Rests on: 5b keep changes small and undo in one step (p. 12), 5d checklist and bans on half-done work (p. 12), the diff-noise point about reordered data (p. 15). Would not apply if: the line-ending change is the sole content of its own commit.
- Do not control DLL or harness behaviour by commenting code in and out; use explicit flags so the variant is recorded and runs can be automated. Rests on: 2h (p. 8). Would not apply if: the change is a one-off local debugging step never committed.
- Keep a small smoke test for each tool and for the patched DLL (a fixed short seeded game with known outputs), run before commits that touch them. Rests on: 2i simple example or test data set (p. 8). Would not apply if: the build takes too long to run per commit, in which case run it per merge request.
- Weigh our check system against the authors' criterion of practices people still use months later: checks whose cost makes people circumvent them fail that criterion and should be simplified rather than extended. Rests on: inclusion criterion (p. 2), change is hard and people switch back (p. 2), CI and coverage pay off only in larger projects (pp. 18-19). Would not apply if: the repository has grown to the many-contributor scale where the authors say CI is invaluable.
- Use one key format across all tables (player id, turn, game id, run seed) so DuckDB joins are reliable. Rests on: 1f unique persistent key in common format (pp. 5-6). Would not apply if: all data come from a single table.
- Keep the C++ patches for the separate GitLab repository as text diffs with stable formatting and a CHANGELOG entry per delivered merge request. Rests on: 5f change log (p. 13), version control record of what actually changed (p. 14). Would not apply if: the GitLab repository's own history already records each delivery with its reason.
