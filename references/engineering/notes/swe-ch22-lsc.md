## What it says
- Introduction: "How many files can you reliably update in a single, simultaneous commit?" -- the opening questions also ask how you would test, review and roll back such a change.
- Introduction: "as a codebase and the number of engineers working in it grows, the largest atomic change possible counterintuitively decreases" -- running all affected presubmit checks and keeping every file up to date becomes difficult.
- What Is a Large-Scale Change?: "an LSC is any set of changes that are logically related but cannot practically be submitted as a single atomic unit." -- the definition; causes are tooling limits, merge conflicts, or federated repositories.
- What Is a Large-Scale Change?: "LSCs at Google are almost always generated using automated tooling." -- categories: cleaning antipatterns, replacing deprecated features, low-level infrastructure improvements such as compiler upgrades, moving users to a newer system.
- What Is a Large-Scale Change?: "The majority of LSCs across Google actually have near-zero functional impact: they tend to be widespread textual updates for clarity, optimization, or future compatibility." -- but they are not limited to behaviour-preserving changes.
- What Is a Large-Scale Change?: "The same tools that make changing thousands of files efficient also scale down to tens of files reasonably well." -- investing early in tooling helps smaller changes too.
- Who Deals with LSCs?: "the infrastructure teams that build and manage the underlying systems are also the ones with the domain knowledge required to fix the hundreds of thousands of references to them." -- first reason for central ownership.
- Who Deals with LSCs?: "Centralization also allows for faster recovery when faced with errors because errors generally fall into a small set of categories, and the team running the migration can have a playbook" -- recovery argument.
- Who Deals with LSCs?: "nobody likes unfunded mandates." -- second reason; footnote 4 defines it as "additional requirements imposed by an external entity without balancing compensation."
- Who Deals with LSCs?: "organic migrations are unlikely to fully succeed, in part because engineers tend to use existing code as examples when writing new code." -- why a team with a vested interest should own the migration.
- Case Study: Filling Potholes: "this difference also led to reduced productivity, and engineers had to remember which file used which separator, and only discovered when they got it wrong after a potentially lengthy compile cycle." -- stl_util.h vs map-util.h; fixed with a couple of weeks of background effort, with build failures quantitatively reduced.
- Case Study: Filling Potholes: "we can make some engineering decisions knowing that they aren’t immutable in the future." -- effect of mature LSC tooling.
- Barriers to Atomic Changes: "In an ideal world, all logical changes could be packaged into a single atomic commit that could be tested, reviewed, and committed independent of other changes." -- the ideal, which becomes less feasible with size and federated repositories.
- Technical Limitations: "most Version Control Systems (VCSs) have operations that scale linearly with the size of a change." -- in centralised VCSs large commits stall other users.
- Technical Limitations: "Splitting the large change into smaller, independent chunks gets around these limitations, although it makes the execution of the change more complex." -- the trade-off.
- Merge Conflicts: "As the number of files in a change increases, the probability of encountering a merge conflict also grows and is compounded by the number of engineers working in the repository." -- with few files, conflicts shrink.
- No Haunted Graveyards: "A haunted graveyard in this sense is a system that is so ancient, obtuse, or complex that no one dares enter it." -- definition.
- No Haunted Graveyards: "Many organizations have bits of software that are old and unmaintained, written by someone long off the team, and on the critical path of some important revenue-generating functionality." -- graveyards in codebases, protected by layers of bureaucracy.
- No Haunted Graveyards: "When software is thoroughly tested, we can make arbitrary changes to it and know with confidence whether those changes are breaking, no matter the age or complexity of the system." -- testing as the counter.
- Heterogeneity: "LSCs really work only when the bulk of the effort for them can be done by computers, not humans." -- computers need consistent environments.
- Heterogeneity: "Simplifying the environment to add more consistency will help both the humans who need to move around in it and the robots making automated transformations." -- recommendation.
- Heterogeneity: "Many of these checks are relevant for teams writing new features, but for LSCs, they just add additional irrelevant complexity." -- presubmit checks; Google made some standard and advises teams to omit special checks for LSCs.
- Testing: "the farther away in the dependency graph a test is from the impacted files, the more unlikely a failure is to have been caused by the change itself." -- observation about transitive test runs.
- Testing: "Finding the root cause of a test failure in a change of 25 files is pretty straightforward; finding 1 in a 10,000-file change is like the proverbial needle in a haystack." -- why small changes are easier to validate.
- Testing: "Because engineer time spent tracking down test failures is much more expensive than the compute time required to run these extra tests, we’ve made the conscious decision that this is a trade-off we’re willing to make." -- the author adds it might not hold for all organisations.
- Case Study: Testing LSCs (Adam Bender): "it is common for a double-digit percentage (10% to 20%) of the changes in a project to be the result of LSCs" -- without good tests this would be impossible.
- Case Study: Testing LSCs: "many LSCs have to plan time to catch downstream clients whose code backslides while the LSC makes its way through the process." -- backsliding during migration.
- Case Study: Testing LSCs: "When a project has flaky tests or is missing unit test coverage, it can require a lot of manual intervention and slow down the entire process." -- cost of weak tests.
- Riding the TAP Train: "The core insight to LSCs is that they rarely interact with one another, and most affected tests are going to pass for most LSCs." -- basis for batched testing; LSCs "tend to be pure refactorings and therefore very narrow in scope, preserving local semantics."
- Riding the TAP Train: "For each change on the train, run a sample of 1,000 randomly-selected tests." -- step 1 of five; then build one uber-change, run the union of affected tests, rerun each nonflaky failure against each change, and report.
- Riding the TAP Train: "The report describes all passing and failing targets and can be used as evidence that an LSC is safe to submit." -- step 5.
- Code Review: "Reviewing large commits can be tedious, onerous, and even error prone, particularly if the changes are generated by hand" -- breaking an LSC into shards makes review easier.
- Case Study: scoped_ptr to std::unique_ptr: "Google’s codebase had more than 500,000 references to scoped_ptr scattered among millions of source files." -- the largest LSC to that point; at its height more than 700 changes and 15,000 files per day.
- Case Study: scoped_ptr to std::unique_ptr: "this one had a very long tail of tracking down various nuanced behavior dependencies (another manifestation of Hyrum’s Law), fighting race conditions with other engineers, and uses in generated code that weren’t detectable by our automated tooling." -- the long tail, handled manually.
- Case Study: scoped_ptr to std::unique_ptr: "were concerned that the resulting changes would themselves be too large to commit atomically." -- why a transitive call-graph rewrite in one commit was rejected.
- Case Study: scoped_ptr to std::unique_ptr: "we were able to finally remove scoped_ptr by first making it a type alias of std::unique_ptr and then performing the textual substitution between the old alias and the new, before eventually just removing the old scoped_ptr alias." -- the alias-then-substitute-then-remove sequence.
- LSC Infrastructure: "perhaps the most important support for LSCs has been the evolution of cultural norms around large-scale changes and the oversight given to them." -- infrastructure is tooling plus norms.
- Policies and Culture: "it became equally easy for a single engineer to impose a burden on a large number of reviewers across the company." -- generation costs fell, review costs did not.
- Policies and Culture: "we want to make sure there is some oversight and thoughtfulness behind them, rather than indiscriminate tweaking." -- reason for the approval process.
- Policies and Culture: "Occasionally, this group might suggest that a cleanup just isn’t worth it: for example, cleaning up a common typo without any way of preventing recurrence." -- a cleanup without recurrence prevention is not worth doing.
- Policies and Culture: "they don’t hold a veto over the broader LSC." -- code owners understand changes but cannot block them; a good FAQ and track record built endorsement.
- Codebase Insight: "it’s important that its human effort scale sublinearly with the codebase" -- change creation tooling should also be comprehensive across the codebase.
- Codebase Insight: "if a change requires more than 500 edits, it’s usually more efficient for an engineer to learn and execute our change-generation tools rather than manually execute that edit." -- rule of thumb; smaller for experienced code janitors; perl, sed or a shell script suffice for small changes.
- Change Management: "Arguably the most important piece of large-scale change infrastructure is the set of tooling that shards a master change into smaller pieces and manages the process of testing, mailing, reviewing, and committing them independently." -- Rosie.
- Testing (LSC Infrastructure): "This is particularly important when applying changes that are not authored by humans." -- testing for machine-generated changes; each shard is tested over the transitive closure of tests it might affect.
- Language Support: "language features such as type aliasing and forwarding functions are invaluable for allowing existing users to continue to function while we introduce new systems and migrate users to them non-atomically." -- support for incremental migration.
- Language Support: "Compiler-based tools along with strong static analysis provide a significant amount of information that we can use to build tools to affect LSCs and reject invalid transformations before they even get to the testing phase." -- static typing makes LSCs easier.
- Language Support: "All of the LSC-generation tools run the automated formatter appropriate to the language being changed as a separate pass so that the change-specific tooling does not need to concern itself with formatting specifics." -- formatting is separate.
- Language Support: "Without automated formatting, large-scale automated changes would never have become the accepted status quo at Google." -- formatter as crucial infrastructure.
- Case Study: Operation RoseHub: "volunteers identified affected projects and sent more than 2,600 patches to upgrade their versions of the Commons library to one that addressed Mad Gadget." -- more than 50 humans did it.
- The LSC Process: "At Google, we aim to design successor systems with a migration path from older systems in mind" -- four phases: authorization, change creation, shard management, cleanup.
- Authorization: "We ask potential authors to fill out a brief document explaining the reason for a proposed change, its estimated impact across the codebase" -- also an FAQ and change description; domain review from API owners.
- Authorization: "for most mechanical LSCs, it’s cheaper to have a single expert understand the nature of the change and build automation around reviewing it properly." -- the global approver.
- Authorization: "The intent of this process is to provide oversight and an escalation path, without being too onerous for the LSC authors." -- the committee has been liberal; footnote 13: rejected only dangerous (NULL to nullptr) or extremely low-value changes (spelling).
- Change Creation: "The change generation process should be as automated as possible so that the parent change can be updated as users backslide into old uses" -- regeneration instead of hand repair; footnote 14 gives copy-and-paste and old habits as causes of backsliding.
- Change Creation: "we want the resulting changes to look as much like human-generated changes as possible." -- hence style guides and formatters.
- Sharding and Submitting: "Rosie takes a large change and shards it based upon project boundaries and ownership rules into changes that can be submitted atomically." -- each shard goes through test-mail-submit; Rosie caps outstanding shards and runs at lower priority.
- Cattle Versus Pets: "nameless and faceless commits that might be rolled back or otherwise rejected at any given time with little cost unless the entire herd is affected." -- treating LSC changes as cattle.
- Cattle Versus Pets: "Having automation means that tooling can be updated and new changes generated at very low cost, so losing a few cattle now and then isn’t a problem." -- why rejection is cheap.
- Testing (Sharding): "independent low-probability events are almost certainties at large enough scale." -- flaky tests seriously affect LSC throughput.
- Testing (Sharding): "recently flaky tests are now ignored when submitting via our automated tooling." -- with the stated risk that a regression is detected only by a flaky test going to failing, rare in practice.
- Testing (Sharding): "For any LSC process, individual shards should be committable independently." -- or dependent changes, such as a header and its implementation, are grouped.
- Mailing reviewers: "For LSCs, we selectively disable certain checks such as those for nonstandard change description formatting." -- such checks are a source of heterogeneity.
- Mailing reviewers: "We also aggressively ignore presubmit check failures that preexist the change in question." -- local owners are responsible for having no preexisting failures.
- Reviewing: "local owners don’t often treat LSCs with the same rigor as regular changes—they trust the engineers generating LSCs too much." -- cursory review in practice.
- Reviewing: "global reviewers use a separate set of pattern-based tooling to review each of the changes and automatically approve ones that meet their expectations." -- they examine manually only anomalies from merge conflicts or tooling malfunctions.
- Submitting: "Technical decisions that used to be final, such as the name of a widely used symbol or the location of a popular class within a codebase, no longer need to be final." -- outcome of the process.
- Cleanup: "it’s important to have a system that prevents additional introductions of the symbol or system that the large-scale change worked hard to remove." -- Tricorder flags new uses of deprecated objects at review time; footnote 16 notes that systems most wanted to decompose organically are the most resilient.
- Conclusion: "all of this happens with only a few dozen engineers supporting tens of thousands of others." -- scale of the effort.
- TL;DRs: "Traditional models of refactoring break at large scales." -- with "An LSC process makes it possible to rethink the immutability of certain technical decisions." and "Making LSCs means making a habit of making LSCs."
- Footnote 6: "We’re doing active research on the best way to determine the “right” set of tests for a given change" -- running all transitive tests is called overkill: "This probably sounds like overkill, and it likely is."

## Readings for our work
- Reading (inference): a change to many files of the DLL (for example, a rename across the code base) should be generated by a script kept in our repository, not edited by hand, so it can be regenerated when the target branch moves and reviewed as one rule instead of many edits. Rests on: LSCs almost always generated by tooling; change generation as automated as possible so it can be updated on backsliding; review of hand-generated large changes is error prone. Would not apply if: the change touches only a few lines where writing the generator costs more than the edits (the 500-edit rule of thumb).
- Reading (inference): formatting must be a separate pass from the change itself; for the CRLF C++ code base, the generator should write the target's line endings and a check should refuse any patch whose whitespace-insensitive diff differs from its raw diff beyond the intended lines. Rests on: formatter runs as a separate pass; changes should look like human changes and fit in. Would not apply if: the target repository enforces line endings itself.
- Reading (inference): split a large patch to the GitLab repository into independently mergeable shards along file or subsystem boundaries, each tested on its own, keeping header and implementation together. Rests on: shards committable independently; small changes easier to diagnose (25 files vs 10,000); merge conflict probability grows with files. Would not apply if: the change is a type change that cannot compile in parts, in which case use the alias-first sequence.
- Reading (inference): for a type or symbol change in the C++ code, add an alias or forwarding function first, migrate uses, then remove the alias, each as a separate commit. Rests on: scoped_ptr removed by alias, substitution, removal; type aliasing and forwarding functions enable non-atomic migration. Would not apply if: MSVC 2003 cannot express the alias needed (for example, template aliases are not available in C++03), then a typedef or wrapper must be checked first.
- Reading (inference): a cleanup without a guard against recurrence is not worth doing; each fix of a past failure (hand-edited generated file, line-ending rewrite) should come with a check that flags the next occurrence at commit time. Rests on: committee rejects cleaning a typo without preventing recurrence; Cleanup needs a system preventing reintroduction (Tricorder). Would not apply if: the failure cannot recur because its cause was removed.
- Reading (inference): checks should be uniform and few; special checks that add friction without catching real problems should be removed rather than accumulated, and preexisting failures should not block an unrelated commit. Rests on: Heterogeneity (irrelevant complexity); selectively disabling nonstandard checks; ignoring preexisting presubmit failures. Would not apply if: a check guards against a failure that has happened in our history.
- Reading (inference): an untested legacy component is a haunted graveyard; before patching untested parts of the DLL, a regression net (fixed-seed harness runs whose outputs are compared) is the precondition. Rests on: No Haunted Graveyards (testing is the counter); Case Study: Testing LSCs (without good tests such work would be impossible). Would not apply if: the patch is provably behaviour-preserving by construction.
- Reading (inference): flaky results corrupt automated judgement at scale; seeded harness runs should be checked for determinism (same seed, same result) before they are used as a test, and a non-deterministic outcome should be flagged rather than silently retried. Rests on: low-probability events are certainties at scale; flaky tests affect throughput; recently flaky tests ignored with a stated risk. Would not apply if: the harness is shown deterministic per seed.
- Reading (inference): review rigor drops when reviewers trust the author; since our checks are often written by the same hand they check, a review of generated changes should be by rule (pattern-based check of every change) with manual attention reserved for anomalies. Rests on: local owners trust LSC engineers too much; global approvers use pattern-based tooling. Would not apply if: an independent reviewer examines every change.
