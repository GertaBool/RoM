# E. F. Codd, A Relational Model of Data for Large Shared Data Banks (Communications of the ACM, Volume 13 / Number 6, June 1970)
Source: lit3/codd-relational/doc.txt. Read: lines 1-2159 (all). The abstract on p. 1 is scrambled in the extraction (lines 2-380) and is not quoted.

## What it says
- p. 1 (1.1 Introduction): "the problems treated here are those of data independence-the independence of application programs and terminal activities from growth in data types and changes in data representation" -- the paper's two problems are data independence and data inconsistency.
- p. 1 (1.1 Introduction): "certain kinds of data inconsistency which are expected to become troublesome even in nondeductive systems" -- the second problem named.
- p. 1 (1.1 Introduction): "It provides a means of describing data with its natural structure only-that is, without superimposing any additional structure for machine representation purposes." -- the claimed advantage over the graph or network model.
- p. 1 (1.1 Introduction): "a basis for a high level data language which will yield maximal independence between programs on the one hand and machine representation and organization of data on the other."
- p. 1 (1.1 Introduction): "forms a sound basis for treating derivability, redundancy, and consistency of relations" -- a further advantage; the network model is said to have "spawned a number of confusions".
- p. 1 (1.1 Introduction): "Implementations of systems to support the relational model are not discussed." -- stated limit of the paper.
- p. 1 (1.2 Data dependencies in present systems): "the variety of data representation characteristics which can be changed without logically impairing some application programs is still quite limited." -- data description tables are a major advance but insufficient.
- p. 1 (1.2): "Three of the principal kinds of data dependencies which still need to be removed are: ordering dependence, indexing dependence, and access path dependence."
- p. 2 (1.2.1 Ordering dependence): "Those application programs which take advantage of the stored ordering of a file are likely to fail to operate correctly if for some reason it becomes necessary to replace that ordering by a different one."
- p. 2 (1.2.1): "fail to make a clear distinction between order of presentation on the one hand and stored ordering on the other." -- said of all well-known marketed systems.
- p. 2 (1.2.2 Indexing dependence): "From an informational standpoint, an index is a redundant component of the data representation." -- an index improves queries and slows insertions and deletions.
- p. 2 (1.2.2): "Can application programs and terminal activities remain invariant as indices come and go?" -- the question posed; in IDS, programs that use indexing chains by name "do not operate correctly if these chains are later removed."
- p. 2 (1.2.3 Access path dependence): "Application programs developed to work with these systems tend to be logically impaired if the trees or networks are changed in structure." -- illustrated by five tree structurings of parts and projects (Structures 1-5).
- p. 3 (1.2.3): "If a program P is developed for this problem assuming one of the five structures above-that is, P makes no test to determine which structure is in effect-then P will fail on at least three of the remaining structures."
- p. 3 (1.2.3): "terminal activities and programs become dependent on the continued existence of the user access paths." -- holds for tree and network models regardless of the stored representation.
- p. 3 (1.2.3): "Such a policy is not practical, because the number of access paths in the total model for the community of users of a data bank would eventually become excessively large." -- said of keeping every access path until all programs using it are obsolete.
- p. 3 (1.3 A relational view of data): "R is a relation on these n sets if it is a set of ntuples each of which has its first element from S1" -- relation in the mathematical sense; Si is the jth domain, n the degree.
- p. 3 (1.3): "this particular representation is not an essential part of the relational view being expounded." -- the array (table) is only an expository representation.
- p. 3 (1.3): the array has five properties: "(1) Each row represents an n-tuple of R. (2) The ordering of rows is immaterial. (3) All rows are distinct. (4) The ordering of columns is significant" -- and (5) columns are labelled with domain names.
- p. 3 (1.3): "two columns may have identical headings (indicating identical domains) but possess distinct meanings with respect to the relation." -- the component relation of Figure 2, used in the parts explosion problem.
- p. 3 (1.3): "The totality of data in a data bank may be viewed as a collection of time-varying relations." -- tuples are inserted, deleted and altered over time.
- p. 4 (1.3): "Users should not normally be burdened with remembering the domain ordering of any relation" -- relations of degree 30 are "not at all uncommon".
- p. 4 (1.3): "we require in each case that the domain name be qualified by a distinctive role name, which serves to identify the role played by that domain in the given relation." -- users deal with domain-unordered relationships.
- p. 4 (1.3): "Each user need not know more about any relationship than its name together with the names of its domains (role qualified whenever necessary)"
- p. 4 (1.3): "We shall call the set of values represented at some instant the active domain at that instant." -- a domain is a pool of values.
- p. 4 (1.3): "Normally, one domain (or combination of domains) of a given relation has values which uniquely identify each element (n-tuple) of that relation. Such a domain (or combination) is called a primary key."
- p. 4 (1.3): "A primary key is nonredundant if it is either a simple domain (not a combination) or a combination such that none of the participating simple domains is superfluous in uniquely identifying each element."
- p. 4 (1.3): "a foreign key if it is not the primary key of R but its elements are values of the primary key of some relation S" -- in supply, supplier, part, project together form the primary key and each alone is a foreign key.
- p. 4 (1.3): "In the user’s relational model there appears to be no advantage to making such a distinction" -- the distinction between entity descriptions and relations between entities.
- p. 4 (1.3): "domains whose elements are atomic (nondecomposable) values" -- simple domains; nonsimple domains have relations as elements (salary history example).
- p. 5 (1.3): "Much of the confusion in present terminology is due to failure to distinguish between type and instance" -- and between user model components and machine representation counterparts, with "record" as example.
- p. 5 (1.4 Normal form): "There is, in fact, a very simple elimination procedure, which we shall call normalization." -- eliminating nonsimple domains, so each relation is a two-dimensional column-homogeneous array.
- p. 5 (1.4): "Starting with the relation at the top of the tree, take its primary key and expand each of the immediately subordinate relations by inserting this primary key domain or domain combination." -- then strike out nonsimple domains and repeat on subtrees (Figure 3a to 3b).
- p. 5 (1.4): the conditions for normalization are "The graph of interrelationships of the nonsimple domains is a collection of trees." and "No primary key has a component domain which is nonsimple."
- p. 5 (1.4): "Further operations of a normalizing kind are possible. These are not discussed in this paper."
- p. 5 (1.4): "not only an advantage for storage purposes but also for communication of bulk data between systems which use widely different representations of the data." -- the communication form would have no pointers, no hash addressing dependence, "no indices or ordering lists."
- p. 5 (1.4): "where R is a relational name; g is a generation identifier (optional); r is a role name (optional); d is a domain name." -- the general name form for data items; g is "needed only when several generations of a given relation exist".
- p. 5 (1.5 Some linguistic aspects): "permits the development of a universal data sublanguage based on an applied predicate calculus." -- first-order suffices if relations are in normal form.
- p. 5 (1.5): "Each declaration of a relation identifies the primary key for that relation. Declared relations are added to the system catalog" -- the host language H indicates how relations are represented in storage.
- p. 6 (1.5): "The universality of the data sublanguage lies in its descriptive ability (not its computing ability)."
- p. 6 (1.5): "Insertions take the form of adding new elements to declared relations without regard to any ordering that may be present in their machine representation."
- p. 6 (1.5): "names are associated with paths (or path types) rather than with relations." -- the burden of the network view on naming.
- p. 6 (1.5): "This is a system feature (missing from many current information systems) which we shall call (logically) symmetric" exploitation of relations -- any combination of arguments as knowns; "symmetry in performance is not to be expected."
- p. 6 (1.5): "then 2n - 1 names have to be coined instead of only n + 1 with direct n-ary notation" -- for nested binary notation; supply needs 7 names instead of 5.
- p. 6 (1.6 Expressible, named, and stored relations): "The named set is the collection of all those relations that the community of users can identify by means of a simple name" -- the expressible set is all relations designated by expressions; "The named set is a subset of the expressible set-usually a very small subset."
- p. 6 (1.6): "Too great a variety leads to unnecessary overhead in storage and continual reinterpretation of descriptions for the structures currently in effect." -- about the class of stored representations to support.
- p. 6 (1.6): "responsibility for providing efficient response and throughput shifts from the individual user to the data system."
- p. 7 (2.1 Operations on relations): "Most users would not be directly concerned with these operations." -- designers and data bank controllers should be thoroughly familiar with them.
- p. 7 (2.1.1 Permutation): "the set of queries answerable by a stored relation is identical to the set answerable by any permutation of that relation." -- storing both is logically unnecessary but performance could make it advisable.
- p. 7 (2.1.2 Projection): "Suppose now we select certain columns of a relation (striking out the others) and then remove from the resulting array any duplication in the rows."
- p. 7 (2.1.3 Join): "Under what circumstances can we combine these relations to form a ... ternary relation which preserves all of the information in the given relations?" -- R is joinable with S if a ternary U projects onto both; the natural join always exists when the shared domains match.
- p. 8 (2.1.3): "Such an element in the joining domain is called a point of ambiguity with respect to the joining of R with S." -- the source of plural joins; if either is a function, the natural join is the only join.
- p. 8 (2.1.4 Composition): "two relations are composable if and only if they are joinable." -- several joins need not give several compositions.
- p. 9 (2.1.4): "A lack of understanding of relational composition has led several systems designers into what may be called the connection trap."
- p. 9 (2.1.4): "if all possible paths are followed from a given supplier via the parts he supplies to the projects using those parts, one will obtain a valid set of all projects supplied by that supplier." -- the erroneous conclusion; it is correct only if the target relation is the natural composition, "for all time."
- p. 9 (2.1.5 Restriction): "A subset of a relation is a relation." -- restriction of R by S as a generalization of restricting a function.
- p. 9 (2.2 Redundancy): "Redundancy in the named set of relations must be distinguished from redundancy in the stored set of representations."
- p. 9 (2.2): "A relation R is O-derivable from a set S of relations if there exists a sequence of operations from the collection 0 which, for all time, yields R from members of S." -- "for all time" because relations are time-varying.
- p. 9 (2.2): "an adequate collection & contains the following operations: projection, natural join, tie, and restriction." -- for the named set in noninferential systems.
- p. 9 (2.2.1 Strong redundancy): "A set of relations is strongly redundant if it contains at least one relation that possesses a projection which is derivable from other projections of relations in the set."
- p. 10 (2.2.1): "In this case the redundancy is obvious: the domain managername is unnecessary." -- employee example with manager# as foreign key.
- p. 10 (2.2.1): "the retention of semiobsolete relationships in the named set so that old programs that refer to them by name can continue to run correctly." -- a reason for strong redundancy (user convenience).
- p. 10 (2.2.1): "extra storage space and update time are consumed with a potential drop in query time for some queries" -- the trade-off when strong redundancies are reflected in the stored set.
- p. 10 (2.2.2 Weak redundancy): "weakly redundant if it contains a relation that has a projection which is not derivable from other members but is at all times a projection of some join of other projections"
- p. 10 (2.2.2): "Generally speaking, weak redundancies are inherent in the logical needs of the community of users. They are not removable by the system or data base administrator."
- p. 10 (2.3 Consistency): "we shall associate with that set a collection of statements which define all of the redundancies which hold independent of time between the member relations."
- p. 10 (2.3): "it cannot deduce the redundancies applicable to the named set. It might, over a period of time, make attempts to induce the redundancies, but such attempts would be fallible." -- because the system lacks semantic information.
- p. 10 (2.3): "we shall call the state (C, 2, V) consistent or inconsistent according as V does or does not satisfy 2." -- the Z of the source is extracted as 2; an algorithm checks a composition constraint column by column.
- p. 10 (2.3): "There are practica1 problems (which we shall not discuss here) in taking an instantaneous snapshot of a collection of relations"
- p. 10 (2.3): "consistency as defined above is a property of the instantaneous state of a data bank, and is independent of how that state came about."
- p. 11 (2.3): "The point is that the system will normally have no way of resolving this question without interrogating its environment" -- an inconsistency may be an omission (more inserts to come) or a faulty input.
- p. 11 (2.3): "In one approach the system checks for possible inconsistency whenever an insertion, deletion, or key update occurs. Naturally, such checking will slow these operations down." -- details are logged and, if not remedied in reasonable time, someone is notified.
- p. 11 (2.3): "Inputs causing the inconsistencies which remain in the data bank state at checking time can be tracked down if the system maintains a journal of all state-changing transactions." -- the batch approach "would certainly be superior if few nontransitory inconsistencies occurred."
- p. 11 (2.4 Summary): "This is bound to become a serious practical problem as more and more different types of data are integrated together into common data banks." -- maintaining consistency.
- p. 11 (2.4): "Neither the purely linguistic details of such a language nor the implementation problems are discussed." -- stated limits.

## Readings for our work
- Analysis code should name columns, not rely on their position or on the row order a log or DuckDB query happens to return; any script that reads a CSV by column index or assumes logs are sorted by turn should be changed to name the column and sort explicitly. Check: reorder rows and columns of an input file and confirm the output is identical. Rests on: ordering dependence (p. 2), domain-unordered relationships with names (p. 4), the ordering of rows being immaterial (p. 3). Would not apply if: a format is defined by position by its producer and cannot carry names (then the position must be declared once in a schema, not scattered in code).
- Each table built from game logs should declare a primary key (e.g. game, seed, turn, player) and the tool should refuse duplicates on it; references between tables (player, unit type) are foreign keys that should be checked to resolve. Rests on: primary and foreign key definitions (p. 4), rows being distinct (p. 3). Would not apply if: a table is a raw event log where duplicates are real events (then a sequence number is part of the key).
- A derived table (or a figure registry entry) must not be stored alongside its source and edited independently; if it is stored, the derivation should be a declared statement that a check re-runs, so a hand-edited generated file is detected. Rests on: strong redundancy and its storage/update cost (p. 10), consistency as satisfying a stated set of constraints (p. 10), the system cannot deduce redundancies itself (p. 10). Would not apply if: the derived file is never committed but always regenerated.
- The pre-commit gate is Codd's per-update checking; it slows commits, and a batch audit with a journal (git history) is the alternative he names. The choice should follow how often lasting inconsistencies occur; record that rate before adding more per-commit checks. Rests on: the two checking approaches (p. 11). Would not apply if: inconsistencies that pass into history are costly to undo (then per-update checking is preferred).
- Consistency checks should test the state of the data, not who produced it or how; a check that trusts a field because a tool wrote it is weaker than one that recomputes the constraint. Rests on: "independent of how that state came about" (p. 10). Would not apply if: the constraint cannot be recomputed from the stored state (then provenance must be recorded).
- Joining game tables through an intermediate (player to unit to city) can produce spurious combinations; such a path-following result should be checked against a directly recorded relation before being reported as fact. Rests on: the connection trap (p. 9), points of ambiguity in joins (p. 8). Would not apply if: the intermediate relation is a function on the join column (no point of ambiguity, p. 8).
- Nested data from saves (per-player lists inside per-turn records) should be flattened to flat tables keyed by the parent key before analysis. Rests on: normalization procedure and conditions (p. 5), bulk communication advantages (p. 5). Would not apply if: the nesting is not a tree or a key is itself nested (conditions on p. 5 fail).
- Keeping an old table name or column so old scripts keep running is a known cost (strong redundancy); old names kept for compatibility should be listed with a date to remove them. Rests on: retention of semiobsolete relationships (p. 10), the impractical policy of keeping every access path (p. 3). Would not apply if: no old consumer exists.
