- p. 1 (Abstract): "while absolute measures of code churn are poor predictors of defect density, our set of relative measures of code churn is highly predictive of defect density." -- headline result.
- p. 1 (Abstract): "our code churn metric suite is able to discriminate between fault and not faultprone binaries with an accuracy of 89.0 percent." -- headline classification result, Windows Server 2003.
- p. 1 (1. Introduction): "true field reliability, as measured by the number of failures found ... by customers over a period of time, cannot be measured before a product has been completed and delivered to a customer." -- the reliability chasm; late information makes corrective action expensive.
- p. 1 (1. Introduction): "It is easily extracted from a system’s change history, as recorded automatically by a version control system." -- churn comes from diff counts of added, deleted and changed lines.
- p. 1 (1. Introduction): "Relative churn measures are normalized values of the various measures obtained during the churn process." -- normalisers include total LOC, file churn, file count.
- p. 1 (1. Introduction): "Studies have shown that absolute measures like LOC are poor predictors of pre- and post release faults [7] in industrial software systems." -- prior evidence; process measures from change history were better indicators than product metrics.

- p. 1 (1. Introduction): "Our basic hypothesis is that code that changes many times prerelease will likely have more post-release defects than code that changes less over the same period of time." -- the basic hypothesis.
- p. 1 (1. Introduction): "We analyzed the code churn between the release of W2k3 and the release of the W2k3 Service Pack 1 (W2k3-SP1) to predict the defect density in W2k3-SP1." -- the study window.

## Readings for our work
- Reading (inference): relative churn of a file in the DLL (lines changed over file size, number of changes per file) is a cheap, version-control-derived signal of where our patches carry risk; files with high relative churn should get more harness runs and review before a merge request. Rests on: p. 1 (churn easily extracted from VCS), p. 4-8 (relative measures correlate with and predict defect density; H1-H4). Would not apply if: our patches are too few for the relation to hold; the result is from one very large system (p. 8).
- Reading (inference): absolute size of a patch is a poor risk signal by itself; a patch's risk statement should be normalised (share of the file changed, number of files touched over files in the subsystem), not given as raw line counts. Rests on: p. 5 (absolute model R2 0.052; step-wise 0.051) vs relative R2 0.811. Would not apply if: the comparison is between patches to the same file, where size is already normalised.
- Reading (inference): a whitespace or line-ending rewrite inflates churned LOC to the size of the file, so it would mark a file as high-churn and mask the real change; line-ending rewrites must be excluded before any churn measure is computed, and a check should refuse patches whose churned LOC equals the file length. Rests on: p. 3 (churned LOC is added plus changed lines by diff; M1 is churned over total LOC). Would not apply if: the diff used ignores line endings.
- Reading (inference): measures that cross-check each other expose anomalies; our figure system could pair related figures (for example, turns played vs log lines vs events counted) so that an abnormal ratio flags a broken extraction. Rests on: p. 1 (measures cross check so they do not conflict), p. 3 (triangulation), p. 8 (abnormal behaviour immediately highlighted). Would not apply if: the figures are independent by construction.
- Reading (inference): a model judged on the data that fitted it overstates itself; any predictor we fit from game logs (for example, of AI outcomes) should be fitted on one random part of the games and tested on the rest, and repeated over several random splits. Rests on: p. 7 (two-thirds split; single-dataset analyses biased; three random splits). Would not apply if: the quantity is computed from a formula and not fitted.
- Reading (inference): state the method's own preconditions and report when they fail, as the authors did with KMO 0.594 for PCA; our analyses should record a failed precondition (for example, too few runs for Welch's test) as a stated limit rather than silently proceed. Rests on: p. 5 (PCA not possible for absolute measures), p. 6 (KMO below 0.6, run anyway for comparison and said so). Would not apply if: the precondition is checked by the tooling and refuses to run.
- Reading (inference): version-control measures miss work done between commits and inflate time measures for long-open edits; any metric we derive from our own git history (time per task, commits per concern) should note that squashed or long-lived work is invisible. Rests on: p. 8 (overlapping edits in one check-out invisible; long check-out inflates weeks of churn). Would not apply if: the metric uses finer-grained logs than commits.
