## Readings for our work
- Reading (inference): the word refactoring does not guarantee behaviour preservation, so a patch to the DLL labelled as restructuring needs its own evidence of unchanged behaviour (for example, identical harness outcomes on a fixed seed set, or identical compiled output), not the label. Rests on: p. 3 (78% define it as improvement; 46% do not mention behaviour preservation), p. 2 (Fowler's transformations do not guarantee preservation). Would not apply if: the change is produced by a mechanical, proven-equivalent transformation.
- Reading (inference): a rule that matters should be protected by a commit gate that checks it mechanically, as the layer map was; for us, the pre-commit gate should check structural rules (no hand edits to generated files, no line-ending change in CRLF files) rather than rely on review. Rests on: p. 6-7 (quality gate checks prevent commits that violate layer constraints; completely automated). Would not apply if: the rule cannot be stated as a mechanical predicate; then a gate only gives false confidence.
- Reading (inference): restructuring should be kept in changes of its own, on its own branch or commit, so its effect can be measured separately from behaviour changes; that is what made the Windows measurement possible. Rests on: p. 3 and p. 7 (refactoring branches isolated and confirmed manually; 1.27% of changes). Would not apply if: the restructuring is too small to separate without cost exceeding its risk.
- Reading (inference): moving or renaming files in the legacy code base raises integration cost for patches against other branches and burdens review; prefer in-place edits, and when a move is needed, deliver it as a separate merge request with no content changes. Rests on: p. 4 (moved files prevented cross-branch patches from applying; more lines/files burden reviewers and collide). Would not apply if: the target repository has no parallel branches and reviewers diff by content, not by path.
- Reading (inference): without a regression net, restructuring of the DLL should not be started; the seeded headless harness is that net and should be run before and after any such change. Rests on: p. 4 (inadequate regression suite gives no safety net; insufficient scenarios, no refactoring), p. 5 (77% fear subtle regression). Would not apply if: the change is verified identical at the binary level.
- Reading (inference): analyse first, then change: before a restructuring, measure the actual dependency structure (which files include which, which functions call which) rather than act on assumptions. Rests on: p. 6 (significant effort to analyse the de-facto structure before decisions), p. 8 (effort focused on the most connected binaries). Would not apply if: the change is local to one function.
- Reading (inference): over-engineering is a named risk; tools and checks added to our repository should each be needed by an actual change, and a check that no change has needed can be removed. Rests on: p. 5 (over-engineering quote: architecture not needed by any feature but all code must adapt). Would not apply if: the check guards a failure that already happened.
- Reading (inference): a correlation between restructuring and fewer defects is not a causal result; when we judge an AI change from observational logs, confounders such as which games or maps were chosen must be named, and a controlled seeded experiment is needed for a causal claim. Rests on: p. 9 (only correlation, not causation; named confounders). Would not apply if: the comparison is already randomised.
