## Readings for our work
- The game AI in the DLL is an E-type program: its value is judged by how it plays against people and other AIs in a game world that its own behaviour shapes, so no specification check can establish that a change is good; only measured play can. This supports judging AI changes by seeded experiment rather than by code review. Rests on: E-programs embedded in the world, correctness of E-programs not the real issue. Would not apply if: the change is a pure fix whose effect follows from a formula (an S-type part).
- Parts of our work are S-type and should be specified exactly: the figure registry, the quote checker, the XML effect lookups. These can be fully checked; keep them small and separate from the judgement parts. Rests on: partitioning into S-programs, S-programs provably correct. Would not apply if: their specification itself keeps changing.
- Track our own process with measures: per commit, files changed in method/ versus research/ and the DLL, and lines added and removed. If the share of commits touching method/ rises without a matching rise in analyses or AI changes, the method has entered growth without output. Rests on: planning based on measures, law IV resource saturation, law II. Would not apply if: the period is a deliberate, bounded build of the method.
- Plan clean-up phases: after a phase of rapid growth (many new tools or checks), the next phase should consolidate, not add. A useful rule from System X: no single change set more than about twice the average size of earlier ones. Check: compare each commit's or merge request's size to the running average. Rests on: incremental growth above twice average gave slipped dates and poor quality, clean-up release due, law V. Would not apply if: the large change is a mechanical rename with no new behaviour.
- For DLL merge requests, changes superimposed on the existing structure make it stiffer; group related AI changes into one coherent patch per concern rather than many small patches on the same functions, and record which functions each patch touches so multiple changes to the same module are visible. Rests on: change upon change, number of module changes measure, system drifts apart. Would not apply if: each patch touches disjoint code.
- A change whose interconnection with the rest is estimated far below comparable changes should be treated as an incomplete design; if a planned AI change touches far fewer call sites than similar earlier changes, look for the missing ones before building. Rests on: ITS interconnectivity ratio 2.4 versus 8.2 for other items. Would not apply if: the new component really is isolated by a narrow interface.
