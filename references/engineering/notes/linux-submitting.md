# The Linux kernel community, Submitting patches: the essential guide to getting your code into the kernel (Linux kernel source tree, Documentation/process/submitting-patches.rst)
Source: lit3/linux-submitting/doc.txt. Read: lines 1-947 (all).

## What it says
- Introduction: "This text is a collection of suggestions which can greatly increase the chances of your change being accepted." -- stated purpose; a large number of suggestions in a terse format.
- Obtain a current source tree: "Most subsystem maintainers run their own trees and want to see patches prepared against those trees." -- the T: entry in MAINTAINERS names the tree.
- Describe your changes: "there must be an underlying problem that motivated you to do this work." -- whether one line or 5000 lines.
- Describe your changes: "Convince the reviewer that there is a problem worth fixing and that it makes sense for them to read past the first paragraph." -- the opening must establish the problem.
- Describe your changes: "Even if the problem was spotted during code review, describe the impact you think it can have on users." -- describe user-visible impact.
- Describe your changes: "include anything that could help route your change downstream: provoking circumstances, excerpts from dmesg, crash descriptions, performance regressions, latency spikes, lockups, etc." -- because most installations run trees that cherry-pick only specific patches.
- Describe your changes: "If you claim improvements in performance, memory consumption, stack footprint, or binary size, include numbers that back them up." -- quantify optimisations.
- Describe your changes: "Describe the expected downsides of your optimization so that the reviewer can weigh costs against benefits." -- trade-offs and non-obvious costs must be stated.
- Describe your changes: "It's important to describe the change in plain English for the reviewer to verify that the code is behaving as you intend it to." -- the description is the reference the code is checked against.
- Describe your changes: "Solve only one problem per patch. If your description starts to get long, that's a sign that you probably need to split up your patch." -- one problem per patch.
- Describe your changes: "the patch (series) and its description should be self-contained." -- do not just say it is version N or rely on earlier versions or URLs.
- Describe your changes: "Describe your changes in imperative mood" -- as if giving orders to the codebase.
- Describe your changes: "If you want to refer to a specific commit, don't just refer to the SHA-1 ID of the commit." -- include the one-line summary, and at least twelve characters of the ID.
- Describe your changes: "Bear in mind that, even if there is no collision with your six-character ID now, that condition may change five years from now." -- short IDs become ambiguous.
- Describe your changes: "Please check the link to make sure that it is actually working and points to the relevant message." -- Link: tags to background.
- Describe your changes: "However, try to make your explanation understandable without external resources." -- summarise the discussion that led to the patch.
- Describe your changes: "Private bug trackers and invalid URLs are forbidden." -- for Closes: tags.
- Describe your changes: "If your patch fixes a bug in a specific commit, e.g. you found an issue using ``git bisect``, please use the 'Fixes:' tag" -- with 12 characters of the ID and the summary, not split across lines.
- Separate your changes: "Separate each **logical change** into a separate patch." -- e.g. bug fixes and performance enhancements apart, an API update apart from a driver using it.
- Separate your changes: "if you make a single change to numerous files, group those changes into a single patch." -- the unit is the logical change, not the file.
- Separate your changes: "each patch should make an easily understood change that can be verified by reviewers. Each patch should be justifiable on its own merits." -- the point to remember.
- Separate your changes: "If one patch depends on another patch in order for a change to be complete, that is OK." -- the dependency is noted in the patch description.
- Separate your changes: "take special care to ensure that the kernel builds and runs properly after each patch in the series." -- because bisect users may split the series at any point.
- Separate your changes: "they will not thank you if you introduce bugs in the middle." -- the reason given.
- Separate your changes: "then only post say 15 or so at a time and wait for review and integration." -- a limit on series size.
- Style-check your changes: "Failure to do so simply wastes the reviewers time and will get your patch rejected, probably without even being read." -- style violations.
- Style-check your changes: "you should not modify the moved code at all in the same patch which moves it." -- the exception when moving code between files.
- Style-check your changes: "This clearly delineates the act of moving the code and your changes." -- and lets tools track the history of the code.
- Style-check your changes: "the style checker should be viewed as a guide, not as a replacement for human judgment." -- checkpatch.pl reports ERROR, WARNING and CHECK.
- Style-check your changes: "You should be able to justify all violations that remain in your patch." -- remaining warnings need reasons.
- Select the recipients for your patch: "You should always copy the appropriate subsystem maintainer(s) and list(s) on any patch to code that they maintain" -- scripts/get_maintainer.pl helps.
- Select the recipients for your patch: "Please do not spam unrelated lists and unrelated people, though." -- a stated limit.
- Select the recipients for your patch: "If you have a patch that fixes an exploitable security bug, send that patch to security@kernel.org." -- not to public lists under embargo.
- Select the recipients for your patch: "Patches that fix a severe bug in a released kernel should be directed toward the stable maintainers" -- with a Cc: stable line in the sign-off area.
- No MIME, no links, no compression, no attachments: "It is important for a kernel developer to be able to" quote "your changes, using standard e-mail tools" -- so patches go inline; git send-email is strongly recommended.
- No MIME, no links, no compression, no attachments: "Be wary of your editor's word-wrap corrupting your patch, if you choose to cut-n-paste your patch." -- a stated warning.
- Respond to review comments: "You must respond to those comments; ignoring reviewers is a good way to get ignored in return." -- a reply is required.
- Respond to review comments: "Review comments or questions that do not lead to a code change should almost certainly bring about a comment or changelog entry so that the next reviewer better understands what is going on." -- answered questions are recorded.
- Respond to review comments: "When sending a next version, add a ``patch changelog`` to the cover letter or to individual patches explaining difference against previous submission" -- and notify commenters.
- Use trimmed interleaved replies: "Top-posting is strongly discouraged in Linux kernel development discussions." -- trim unneeded quotations.
- Don't get discouraged - or impatient: "You should receive comments within a few weeks (typically 2-3); if that does not happen, make sure that you have sent your patches to the right place." -- wait at least one week before resubmitting or pinging.
- Don't get discouraged - or impatient: "only applies to resubmission of a patch or patch series which have not been modified in any way from the previous submission." -- the RESEND marker.
- Sign your work: "To improve tracking of who did what, especially with patches that can percolate to their final resting place in the kernel through several layers of maintainers" -- the reason for the sign-off procedure.
- Sign your work: "The sign-off is a simple line at the end of the explanation for the patch, which certifies that you wrote it or otherwise have the right to pass it on as an open-source patch." -- via the Developer's Certificate of Origin 1.1.
- Sign your work: "SoB chains should reflect the **real** route a patch took as it was propagated to the maintainers and ultimately to Linus" -- the first entry signals primary authorship.
- When to use Acked-by:, Cc:, and Co-developed-by:: "The Signed-off-by: tag indicates that the signer was involved in the development of the patch, or that he/she was in the patch's delivery path." -- definition.
- When to use Acked-by:, Cc:, and Co-developed-by:: "It is a record that the acker has at least reviewed the patch and has indicated acceptance." -- Acked-by is less formal than Signed-off-by.
- When to use Acked-by:, Cc:, and Co-developed-by:: "maintainers may use it to signify that they are OK with a patch landing, but they may not have reviewed it as thoroughly as if a Reviewed-by: was provided." -- Acked-by is less formal than Reviewed-by.
- When to use Acked-by:, Cc:, and Co-developed-by:: "Acked-by: does not necessarily indicate acknowledgement of the entire patch." -- it may cover only one subsystem's part.
- When to use Acked-by:, Cc:, and Co-developed-by:: "every Co-developed-by: must be immediately followed by a Signed-off-by: of the associated co-author." -- and the last sign-off is the submitter's.
- Using Reported-by:, Tested-by:, Reviewed-by:: "A Tested-by: tag indicates that the patch has been successfully tested (in some environment) by the person named." -- informs maintainers that testing was done.
- Using Reported-by:, Tested-by:, Reviewed-by:: "I have carried out a technical review of this patch to evaluate its appropriateness and readiness for inclusion into the mainline kernel." -- part (a) of the Reviewer's statement of oversight.
- Using Reported-by:, Tested-by:, Reviewed-by:: "Any problems, concerns, or questions relating to the patch have been communicated back to the submitter." -- part (b); the reviewer is satisfied with the response.
- Using Reported-by:, Tested-by:, Reviewed-by:: "I do not (unless explicitly stated elsewhere) make any warranties or guarantees that it will achieve its stated purpose or function properly in any given situation." -- part (d), the limit of a review.
- Using Reported-by:, Tested-by:, Reviewed-by:: "A Reviewed-by tag is a statement of opinion that the patch is an appropriate modification of the kernel without any remaining serious technical issues." -- offered by a reviewer with known identity who has done the work.
- Using Reported-by:, Tested-by:, Reviewed-by:: "However if the patch has changed substantially in following version, these tags might not be applicable anymore and thus should be removed." -- removal is noted in the changelog after the separator.
- Using Reported-by:, Tested-by:, Reviewed-by:: "A Fixes: tag indicates that the patch fixes a bug in a previous commit." -- it shows where an issue originated and which stable versions need the fix.
- Tagging people requires permission: "all except for Cc:, Reported-by:, and Suggested-by: need explicit permission of the person named." -- a rule on tags.
- Using Assisted-by:: "If you used any sort of advanced coding tool in the creation of your patch, you need to acknowledge that use by adding an Assisted-by tag." -- failure may impede acceptance.
- The canonical patch format: "The tools cannot create the necessary text, though, so read the instructions below anyway." -- format-patch formats, but does not write the explanation.
- The canonical patch format (Subject Line): "Bear in mind that the ``summary phrase`` of your email becomes a globally-unique identifier for that patch." -- it propagates into the changelog and is what people see in git log --oneline.
- The canonical patch format (Subject Line): "it must describe both what the patch changes, as well as why the patch might be necessary." -- in no more than 70-75 characters; not a filename, not repeated across a series.
- The canonical patch format (Subject Line): "This assures that developers understand the order in which the patches should be applied" -- numbering like 1/4 ... 4/4.
- The canonical patch format (Explanation Body): "should make sense to a competent reader who has long since forgotten the immediate details of the discussion that might have led to this patch." -- the body goes into the permanent changelog.
- The canonical patch format (Explanation Body): "it can give the reader the needed details to grasp the reasoning for **why** the patch was created." -- weeks, months or years later.
- The canonical patch format (Explanation Body): "If a patch fixes a compile failure, it may not be necessary to include _all_ of the compile failures" -- just enough to be found.
- Backtraces in commit messages: "Copying the full dmesg output verbatim, however, adds distracting information like timestamps, module lists, register and stack dumps." -- distil the relevant information.
- Commentary: "The ``---`` marker line serves the essential purpose of marking for patch handling tools where the changelog message ends." -- diffstat and comments go after it.
- Commentary: "Other comments relevant only to the moment or the maintainer, not suitable for the permanent changelog, should also go here." -- version notes go below the separator and are stripped on apply.
- Explicit In-Reply-To headers: "for a multi-patch series, it is generally best to avoid using In-Reply-To: to link to older versions of the series." -- to avoid a forest of references.
- Providing base tree information: "it is absolutely necessary for them to know what is the base commit/branch your work applies on" -- and even more for automated CI.
- Providing base tree information: "you can automatically include the base tree information in your submission by using the ``--base`` flag." -- format-patch adds a base-commit trailer.
- Providing base tree information: "Make sure that base commit is in an official maintainer/mainline tree and not in some internal, accessible only to you tree - otherwise it would be worthless." -- a private base is useless to others.
- Tooling: "Many of the technical aspects of this process can be automated using b4" -- dependencies, checkpatch, formatting and sending.

## Readings for our work
- Inference: every claimed AI improvement in a commit or merge request must carry the numbers that back it, with the downsides stated, so the reviewer can weigh them; for us those numbers come from the seeded experiments and the figure registry. Check: no message claims an improvement without a registry figure or experiment reference. Rests on: Describe your changes (quantify optimisations, describe downsides). Would not apply if: the change makes no claim of improvement (a pure refactor).
- Inference: in a DLL merge request, a code move and a change to the moved code must be separate commits, and so must a whitespace or line-ending change and a logic change; a patch whose diff rewrites every line of a CRLF file is a separate concern that must not ride along with a fix. Check: git diff --stat and git diff -w agree in size for a logic commit. Rests on: Style-check (do not modify moved code in the same patch); Separate each logical change. Would not apply if: the upstream asks for a reformat together with a change (it does not here).
- Inference: each commit in a series must build and run on its own, so that a bisect over the DLL history or our repository history never lands on a broken state. Check: build or run the checks at every commit of a series before delivery. Rests on: Separate your changes (builds after each patch; bisect). Would not apply if: the series is squashed into one commit on delivery.
- Inference: an automated checker is a guide, not a replacement for judgement, and every remaining warning must be justified in writing; a gate that can be passed only by suppressing it is evidence of a problem. Rests on: Style-check (checker as guide; justify violations). Would not apply if: the check is a hard correctness property (e.g. a figure without a source), where no exception is justified.
- Inference: a review tag means the reviewer did a technical review and raised all concerns with the submitter, and it lapses when the change changes substantially; a check passing on an earlier version is not evidence for the current one. For our gate: re-run the checks on the final commit, and do not carry over an approval across substantive changes. Rests on: Reviewer's statement of oversight; removal of tags after substantial change. Would not apply if: the later change is trivial and stated as such.
- Inference: a merge request to the GitLab DLL repository must name its base commit in the upstream tree (not a private branch), so that the maintainer can apply it with git am or merge it without conflicts. Rests on: Providing base tree information bullets. Would not apply if: GitLab shows the base of the merge request itself (it does for branch-based merge requests; patches by mail need the base-commit trailer).
- Inference: version notes, session notes and process chatter belong below the --- separator or in the merge request discussion, not in the permanent commit message, which must make sense to a reader who has forgotten the discussion. Rests on: Explanation Body; Commentary bullets. Would not apply if: the note is part of the reason for the change (then it belongs in the body).
- Inference: use of an AI coding tool should be acknowledged in a trailer on patches to upstream projects. Rests on: Using Assisted-by. Would not apply if: the upstream project has a different or no policy (this rule is the kernel's).
- Inference: a commit referencing another commit should give at least 12 characters of the hash and its subject, so that references in our documents and in the register stay unambiguous. Rests on: Describe your changes (commit references). Would not apply if: the reference is generated by a tool that already resolves it.
